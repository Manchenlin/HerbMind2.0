# HerbMind 平台技术答辩手册

> 用途：明天向老师汇报、以及面试时讲这个项目。
> 原则：**只说代码里真的有的**。凡是"规划中/未实现"的地方，本文都单独标出来了——被追问时坦白讲缺口，比被当场抓包强。
> 所有数字来自 2026-11-11 实核（`scripts/smoke.py` 基线、`mvn test`、`pytest`、`vitest` 实际输出）。

## 一、30 秒讲完这个项目

**一句话**：把一个中医古籍阅读平台做成"能查证、能练习、能问答"的完整产品，数据、检索、图谱、Agent 四条线都跑通，并且**每一条技术选择都对应一个具体的学习痛点**。

**规模（都是可核对的数字）**

| 维度 | 数字 |
|---|---|
| 语料 | 1 本书、73 个目录节点（4 章 / 38 节）、598 条原文单元（全部 1024 维向量） |
| 结构化数据 | 方剂 245、医案 290、条文 568、方剂组成 1,315 条 |
| 图谱 | 245 个方剂节点、376 味药、1,288 条组成关系（Neo4j） |
| 后端 | 10 个 Maven 模块、8 个可运行服务、41 张表 / 73 个索引 |
| 前端 | 36 个页面 / 35 条路由，全部懒加载 |
| Agent | FastAPI + LangChain，5 个工具，同步问答 + SSE 流式 |
| 测试 | Agent 208 例、前端纯函数 32 例、后端 23 例、数据冒烟 11 项 |

**技术栈三条线**
- 前端：Vue 3.5 + TypeScript strict + Vite 5 + vue-router + axios。**没有任何 UI 库、没有任何图表库**，图谱和图表全部手写 SVG。
- 后端：Java 17 + Spring Boot 3.3.5 + Spring Cloud 2023（Gateway）+ MyBatis-Plus + PostgreSQL 17/pgvector + Neo4j 5。
- Agent：Python 3.11 + FastAPI + LangChain 1.x + bge-m3（1024 维）+ Qwen 系模型。

## 二、系统全景（被问"你怎么分的服务"就讲这张）

```
浏览器
  │  /api/biz/**        /api/agent/**
  ▼                          ▼
herbmind-gateway :8080  ← Spring Cloud Gateway
  │  两条静态路由 + JWT 全局过滤器（HS256，白名单 3 个，重写 X-User-Id）
  ├──────────────► herbmind-bff :8090（前端唯一业务入口，OpenFeign 转发 + 分区降级 + R<T> 包装）
  │                    │
  │                    ├─► svc-identity  :8081  登录注册 / 收藏 / 笔记 / 讨论
  │                    ├─► svc-catalog   :8082  目录树 / 方剂 / 医案 / 条文 / 原文 / 语料登记
  │                    ├─► svc-search    :8083  四腿召回 + RRF 融合
  │                    ├─► svc-training  :8084  出题 / 评分 / 错题 / 背诵 / 盲盒
  │                    ├─► svc-graph     :8085  Neo4j 邻居 / 子图 / 相似度地图 / 路径
  │                    └─► svc-insight   :8086  用药 / 证候 / 趋势 / 导出
  └──────────────► agent :8091（FastAPI + LangChain，自己再回调上面几个 svc 的 /internal/**）

数据层：PostgreSQL 5432（pgvector 1024 维 + HNSW）/ Neo4j 7687 / Redis 6379 / Nacos 8848
```

**为什么这么分**（面试常问"为什么微服务"）：
1. **按读路径分，不按表分**。阅读走 catalog、搜索走 search、图谱走 graph，各服务可以独立重启、独立压测；改检索 SQL 不用重启整个后端。
2. **7 个 svc 只暴露 `/internal/**`，不进网关**。外部只能打到 BFF，svc 之间靠 Feign 契约调用，攻击面收缩到两个入口。
3. **BFF 做聚合与降级**。首页要同时取 catalog 的统计、书单、日推、图谱预览和 search 的热词，任何一个挂了只影响那一块（`HomeService` 逐分区 try/catch，把失败分区名放进 `degraded` 返回给前端），不会整页白屏。

## 三、前端：看得见的功能 → 接口 → 技术 → 用户价值

### 3.1 五个功能块（讲给老师听就照这个顺序）

| 块 | 页面 | 调用的接口 | 对用户的作用 |
|---|---|---|---|
| **读** | 首页 `/`、书架 `/shelf`、典籍浏览 `/library`、节点 `/node/:id`、方剂 `/formula/:id`、医案 `/case/:id`、条文 `/quote/:id` | `/biz/home`、`/biz/catalog/books`、`/biz/library/tree`、`/biz/catalog/node/{id}`、`/biz/catalog/node/{id}/content`、`/biz/formula/{id}/page`、`/biz/case/{id}/page`、`/biz/quote/{id}/page` | 按原书「章→节→类」顺序读，正文、方剂、医案、条文四类内容在同一页并存，不用来回跳 |
| **查** | 检索工作台 `/search`、结果分面 `/search/result`、条文反向索引 `/search/quote-index`、智能问答 `/ask` | `/biz/search`、`/biz/search/facets`、`/biz/search/quote-index`、`/api/agent/ask/sync` | 一个词同时命中方剂/医案/原文/条文；问答给出引用卡和检索耗时，能点回原文核对 |
| **练** | 练习台 `/train`、答题、评分报告、案例盲盒、背诵打卡、错题本、学习路径、学习档案 | `/biz/train/options`、`/biz/train/session`、`/biz/train/answer`、`/biz/train/report/{id}`、`/biz/train/recite`、`/biz/train/blindbox`、`/biz/me/wrong`、`/biz/me/path`、`/biz/me/profile` | 出题→作答→按药味/辨证/治法三维评分→错题回流→下一轮只练错的 |
| **研** | 科研工作台 `/research`、数据导出 `/research/export` | `/biz/insight/herbs`、`/biz/insight/syndrome`、`/biz/insight/trend`、`/biz/insight/research-pack`、`/biz/insight/export` | 用药频次、证候分布、趋势曲线，可导出研究包做论文素材 |
| **图** | 图谱探索 `/graph`、方心子图 `/graph/formula/:id`、相似度地图 `/graph/map` | `/biz/graph/neighbors`、`/biz/graph/formula/{idOrName}`、`/biz/graph/map` | 看一首方由哪些药组成、和哪些方组成相近；地图上直观看全库方剂的"远近" |

> 另有「我的」（收藏/笔记/错题/方证库）、治理后台三页（治理页仍是示意数据，见第九节）。

### 3.2 六个能明显看到的技术细节（这些是"炫技但有用"的重点）

| 交互 | 怎么做的 | 为什么这么做 |
|---|---|---|
| **阅读页书内搜索** | 搜索时可勾"只搜当前节点"，把 `nodeId` 传给 `/biz/search`；后端按节点子树 + `meta_jsonb.chapter/section` 匹配 | 读某一节时最常问"这节里有没有提到 X"，不把范围收紧会搜出一堆别的章节 |
| **方名悬浮卡** | 正文按本节方名做**最长优先**切词，悬停 `Teleport` 到 body 的卡片，显示主治/组成/页码；`matchMedia('(hover: hover)')` 为假时降级为点击跳转 | 读原文遇到方名不想丢上下文；触屏没有 hover，硬做悬停等于点了没反应 |
| **字号 + 主题** | 13–22px + 日间/泛黄/夜间三套，存 `localStorage`，通过 CSS 变量 `--reader-font/--reader-bg/--reader-fg` 下发，只作用于阅读区 | 古籍阅读时长长，夜间和字号是刚需；用变量而不是换整套 CSS，是为了不污染其他页面 |
| **阅读进度记忆** | `hm:reading:{bookId}` 存 `{nodeId, scrollY}`，滚动 800ms 节流写一次；恢复时 `nextTick` + 300ms 二次滚动补偿异步正文高度 | 用户不会一次读完一节，下次打开要直接落回原处；正文异步加载导致首帧高度不够，所以补一次滚动 |
| **章级不拉整章正文** | 点章只取摘要（子节点/方剂/医案），正文按节取；`/content` 按需请求 | 实测第四章 239 段 / 16.2 万字 / 接口 489 KB，一次拉会把页面拖住；单节最大只有 26 段，按节读体验更好 |
| **手机端目录折叠** | `@media(max-width:860px)` 下目录 `display:none`，`.is-open` 才展开，桌面端按钮隐藏 | 手机上目录占满首屏，正文永远要滑半天 |

图谱侧还有两处：**相似度地图坐标完全用后端返回的归一值**（前端不重排，保证"距离"有统计意义）、**hover 邻接高亮**（非邻居整体降到 0.35 透明度）。

### 3.3 前端技术点（面试问"前端怎么做的"）

1. **47 个 `.vue` 全部 `<script setup lang="ts">`**，没有一处 Options API。
2. **TypeScript strict**，`npm run build` = `vue-tsc --noEmit && vite build`，类型错直接阻断打包。
3. **axios 统一封装**：请求拦截塞 `Bearer` token；响应拦截剥 `R<T>` 外壳、`code!==0` 抛错；**401 清 token 跳登录、403 故意不清**（权限不足不是登录失效）；错误对象挂 `status` 供上层做 404/500 分支。
4. **composable 做单例缓存**：`useBooks` 模块级缓存 + inflight 去重，全站书单只请求一次。
5. **路由懒加载 + 自动分包**：35 条路由全部 `() => import()`，每个页面一个 chunk，入口包 162 KB。
6. **CSS 变量 + scoped**：一份 `theme.css` 定义设计令牌，组件内 `<style scoped>`；阅读主题靠变量覆盖。
7. **纯手写 SVG**：图谱、雷达图、相似度地图都是内联 SVG + 自研布局纯函数（`utils/graphLayout.ts`），**不引 d3**。

> 为什么不用 UI 库/图表库：视觉基线是我们自己的 `theme.css`，引 Element Plus 会带来一整套互斥的样式与体积；图表只有三种形态，自己写反而更可控，还能对布局函数写单测（32 例就是测这个）。

## 四、后端：技术底蕴在哪

### 4.1 网关（Spring Cloud Gateway）

- 两条静态路由：`/api/biz/**` → BFF:8090；`/api/agent/**` → Agent:8091。
- **JWT 全局过滤器**（`GlobalFilter`，`Ordered(-100)`）：HS256 校验，与身份服务共用同一 secret；白名单只有 3 条（登录、注册、agent 健康检查）。
- **身份头可信边界**：先 `remove("X-User-Id")` 再 `set`，防客户端伪造；下游 agent 强制要求该头存在，形成"只能经网关访问"的闭环。
- 401 也返回 `R` 结构（`{code:401,...}`），前端不用为网关错误写第二套解析。
- **没有限流**（没接 Redis RateLimiter）——这是已知缺口，见第九节。

### 4.2 BFF（前端唯一入口）

- **OpenFeign 声明式转发**，Feign 接口定义在契约模块，BFF 只依赖 interface，不依赖实现。
- 超时显式配：`connectTimeout 2000 / readTimeout 10000`。
- **聚合 + 分区降级**：首页五个分区各自 try/catch，失败的只丢那一块并写进 `degraded` 列表。
- **异常分诊**：`GraphExceptionAdvice` 把 Feign 的 4xx/5xx、连接失败映射成 `4000/4040/5030`，而不是让公共 handler 一律兜成 `5000`——否则前端无法区分"没这个实体"和"服务炸了"。

### 4.3 契约层

约 40 个 VO/DTO + 6 个 Feign Client（Catalog / Search / Graph / Insight / Identity / Training）。
每个 Client 的 `url` 都是 `${herbmind.svc-xxx-url:http://localhost:端口}`，**换成注册中心只需改配置，不改业务代码**。
约定：svc 的 `/internal/**` 返回**裸 DTO**，由 BFF 包 `R<T>`——外壳只在一层出现，避免嵌套。

### 4.4 检索（最能讲的一块）

`svc-search` 用**纯 JdbcTemplate 手写 SQL**，一次查询四腿召回 + RRF 融合：

| 腿 | 实现 | 解决什么 |
|---|---|---|
| 向量 | pgvector `<=>` 余弦 + HNSW 索引 | 语义相近（"怕冷无汗" ↔ "恶寒无汗"） |
| 全文 | `search_tsv` 生成列 + `plainto_tsquery('jiebacfg')` + `ts_rank_cd` | 精确词命中 |
| 词项 | 中文 2-gram + `pg_trgm` 模糊 | 分词器不佳时的兜底（长尾词、错字） |
| 条文 | 条文号/正则匹配 | 用户直接输「35 条」这种查法 |

- **RRF（Reciprocal Rank Fusion）**按名次融合，不用人工调权重。
- **显式降级档位**：`mode = browse / hybrid / fulltext / fuzzy`；嵌入服务没配时自动跳过向量腿且不报错。
- 索引：HNSW 余弦 + GIN 全文 + trgm，共 73 个索引的一部分。

> 为什么不用 Elasticsearch：数据量只有几百条单元，PostgreSQL 一个库同时能存向量、全文、关系，少一个中间件就少一处不一致；HNSW 在万级以下完全够用。

### 4.5 数据层设计

- **`content_unit` 是唯一检索入口**：所有正文（方剂正文、医案、理论、表格）都落在一张表，`unit_type` 区分，`embedding vector(1024)`，`search_tsv` 是 `GENERATED ALWAYS ... STORED` 生成列（**禁止 ORM 映射**，否则写入报错）。
- **`book_node` 是唯一目录表**：自引用树（chapter/section/category/unit），一本书的目录结构不建第二张表——这是"语料可插拔"的基础。
- **Neo4j 只存两跳以内需要的关系**：`(:Formula)-[:COMPOSED_OF {dose,unit,role}]->(:Herb)`。Jaccard 相似度**不在图里算**，用 PG 数据在服务端算，避免图库承担统计职责。
- **没有 Flyway**：建表靠 PG 容器 `initdb` 按序执行 `database/pg/00→04`，全部写成幂等（`IF NOT EXISTS`），换机器 `docker compose up` 就建好。
- 中文分词**诚实说明**：`pg_jieba` 是"有则装、无则用 `COPY OF simple` 兜底"，配置名固定 `jiebacfg`；镜像默认不含 pg_jieba，所以现在分词效果有限，靠 2-gram 词项腿补。

### 4.6 工程化

| 项 | 现状 |
|---|---|
| 统一响应 / 异常 | `R<T>` + `@RestControllerAdvice`，HTTP 状态码与 body 里的 code 同步正确 |
| 数据冒烟 | `scripts/smoke.py` 11 项：表行数基线、向量覆盖率与维度、BFF `code=0`、Neo4j 节点数，失败非零退出 |
| CI | **只有 Agent 的 pytest**（`.github/workflows/agent-tests.yml`，`agent/**` 变更触发）；后端 `mvn test` 没有 CI |
| 容器化 | 只有中间件的 compose，**没有 Dockerfile**（业务服务跑 IDE/命令行） |
| 监控 | 只有 Agent 自己实现的 `/api/agent/health`（探测 PG/Neo4j/Redis/LLM）；Java 侧未引 actuator |

### 4.7 Nacos 与 Redis 的真实状态（必须主动说，别等被问）

- **Nacos**：容器起来了（8848/9848），但 **backend 代码完全没接**——没有 nacos 依赖、没有 `bootstrap.yml`、没有 `@EnableDiscoveryClient`/`@RefreshScope`，网关与 Feign 全是 `http://localhost:8xxx` 静态地址。所以现在**既不是注册发现也不是配置中心**。
  理由：单机开发阶段静态地址排错最快；接入只需要加依赖 + 把 Feign 的 `url` 换成服务名（属性已经预留）。
- **Redis**：业务侧零使用，只有 Agent 探活 `PING`。Agent 的限流是**进程内滑动窗口**（60s/20 次），注释里写明多副本不准、要 Redis 得等后续。

这么讲不是减分项：**知道哪些是真做了、哪些是留了接口没接**，本身就是工程判断力。

## 五、Agent（域3 核心，面试主战场）

### 5.1 一次问答发生了什么

```
用户问题
 → ① 主召回（retriever）：直接查 PG content_unit，向量召回 + 类型配额
      formula 60% / case 40% / 理论 node 独立配额，相似度阈值 0.5
 → ② 工具取证（模型自己决定调哪个，最多 3 轮、总预算 15s）
      search_formula / search_case / semantic_recall / graph_neighbors / syndrome_score
 → ③ 组织回答（LLM），只允许引用检索到的编号
 → ④ 返回 citations（每条带 snippet / 类型 / score / 原文链接）+ 耗时与 token 数
```

### 5.2 值得讲的三件事

1. **手写工具调用循环，不用 AgentExecutor**
   `runner.py` 里是显式 while 循环：**轮次上限 3 + 时间预算 15s + 单工具超时与重试 + `CancelledError` 透传**。
   为什么不用现成框架：我们要在"决策轮"里去掉检索资料、只发问题——实测带着大段资料 + `tool_choice=required` 会让小模型撞满 `max_tokens` 返回空 choices 直接 `IndexError`。这种细节只有自己写循环才控得住。
2. **SSE 做成契约，不是"能推就行"**
   事件时序固定：`retrieval start → retrieval done → tool* → citation → token → done`；
   `citation.index` 与正文 `[n]` 严格对应；`done` 里带 **`illegalCitations`**——模型如果引用了不存在的编号，前端据此剔除；
   响应头带 `X-Accel-Buffering: no` 防 Nginx 缓冲，并且注释解释了为什么不加 `Connection: keep-alive`（逐跳头，HTTP/2 禁传）。
3. **红线用代码兜，不靠提示词**
   设计红线是"只查证+引用，不推断功效、不给剂量"。落地方式是：
   - `dosage_convert` 工具**故意不挂载**（`dosage_rule` 表 0 行，挂了模型就会编剂量）；
   - 练习评分用确定性算法：药味 **F1 = 2PR/(P+R)**，加权 0.3/0.4/0.3；代码注释如实标注"辨证分/治法分只是字面重合度，不懂近义词"；
   - 图谱路径查询强制 `LIMIT` + 跳数上限，禁止无界 `[*]`。

### 5.3 Agent 侧技术参数

| 项 | 值 |
|---|---|
| 端点 | `health`、`ask/sync`（同步）、`ask`（SSE）、`formula/diff`（纯规则零 LLM）、`history` |
| 工具数 | **5 个**，全部 async（httpx），数据源走各 svc 的 `/internal/**` |
| 多轮 | 不用 checkpointer，从 `agent_message` 表回填最近 6 条 |
| 嵌入 | bge-m3，1024 维，与库里锁死（换模型 = 全量重算，不是可调项） |
| 单测 | 208 例（工具、循环、SSE、历史、diff、健康检查） |

## 六、语料插拔式：数据模型怎么支撑"一本变书架"

### 6.1 已经做到的

- **三张表撑起所有书**：`book`（书元数据 + `book_type ∈ fz/bencao/drug/case` + `ingest_status`）→ `book_node`（自引用目录树，唯一目录表）→ `content_unit`（唯一检索入口，统一类型 + 向量）。
- 加一本**方证类**书：只插 `book` + `book_node` + `content_unit`，**不用改表结构**，前端书架自动多一本（`/biz/catalog/books` 是查表不是写死）。
- 前端已经有导入入口：书架 → `/shelf/import` → `POST /biz/catalog/import`。

### 6.2 导入现在到哪一步（如实说）

`importBook()` 目前只做**登记**：校验书名与 `book_type`，插一行 `book`，`ingest_status = draft`，返回"待复核"。
**解析与向量化不在请求里做**——审核通过后由 ETL 执行（`import_docx_gap.py` / 迁移脚本）。

为什么这么设计：解析一本 400 页的书 + 调几百次 embedding 是分钟级任务，塞进 HTTP 请求会超时；而且未经审核的语料直接进检索会污染答案。所以流程是 **登记 → 审核 → 解析 → 入库 → 建图**。

### 6.3 删除功能：还没实现（规划方案）

现状：`book` 表有 `ingest_status`，但**没有下架/删除接口**。要做的话，删除必须是"软删 + 级联清单"，不能一条 `DELETE` 了事：

1. `book.ingest_status = 'archived'`（软删，保留审计），前端书架过滤掉；
2. 级联范围：`book_node`（含子树）→ `content_unit`（按 `ref_id`/`meta` 归属）→ `formula` / `case_record` / `classic_quote` → Neo4j 里对应的 `(:Formula)` 与 `(:Herb)` 孤立节点；
3. **向量不需要单独删**（跟着 `content_unit` 行走），但 HNSW 索引需要 `VACUUM` 才回收空间；
4. 跨库一致性：PG 与 Neo4j 无法同事务，先用 `relation` 记一条待清理任务，后台补偿删除（宁可残留也不能出现"图里有、库里没有"）。

### 6.4 还没解决的欠账（面试官会追问）

- `case_record` **没有 `book_id` 也没有 `node_id`** → 医案无法直接归属到书，现在靠 `main_formula_id` 间接挂；
- `formula` 只有 `node_id`，且**不是全部有值**（历史数据有空白）；
- **本草/药品类必须建新表**（41 张表里没有 `herb`/`drug` 实体，只有图谱里的 `:Herb` 名字）；
- Neo4j 建图脚本只建 `Formula/Herb/COMPOSED_OF`，**没有 `:Book` 节点与 `IN_BOOK` 关系**——接第二本方证书后，两本书的方剂在图里会混成一片。

这四条是"插拔式"从口号变成现实的关键，也是最容易在答辩里被问穿的地方，主动讲。

## 七、学习模块：现在能学什么、下一步优化什么

### 7.1 已实现的闭环

```
选范围（章/节/类）→ 出题（/biz/train/options → /biz/train/session）
  → 作答（症状/舌脉 → 辨证/治法/处方用药，POST /biz/train/answer）
  → 规则评分（RuleScorer）
       药味：F1 = 2PR/(P+R)，权重 0.3
       辨证：字面重合度，权重 0.4
       治法：字面重合度，权重 0.3
  → 报告（/biz/train/report/{id}）→ 错题进 /biz/me/wrong → 下一轮只练错的
```

配套：**案例盲盒**（随机抽医案，先猜再揭晓）、**背诵打卡**（条文背诵，按日期记录）、**学习路径**（按目录顺序推进）、**学习档案**（正确率/覆盖度/薄弱章节）。

### 7.2 优化方向（讲的时候要落到"为什么对学习有用"）

| 优化 | 做什么 | 为什么有用 |
|---|---|---|
| 辨证分升级 | 现在的字面重合度 → 换成结构化证候要素比对（证型 + 病位 + 病性），复用 `syndrome_score` | 学生写"恶寒发热"和标准答案"恶寒、发热"该算对，现在是两回事 |
| 自适应出题 | 按错题分布调权重（IRT 思路：答对降权、答错升权），而不是随机抽 | 只练不会的，时间利用率翻倍 |
| 评分解释 | 报告里逐味药说明"你多写了 X、漏了 Y"，附原书依据 | 分数之外要知道错在哪，否则只是难堪 |
| Agent 教练（`coach`） | 多轮追问式辨证训练（给症状 → 反问 → 学生逐步收敛） | 真实临床是问出来的，不是一次作答 |

## 九、未来方向（你点名的那些，逐条给"做什么 / 为什么值得做 / 难点"）

### 9.1 Agent 做得更完善

**(1) 多模态：舌象/图片**
- 做什么：新增 `POST /api/agent/vision`，接收舌象/面色照片，用视觉模型输出"舌质/舌苔/润燥"等结构化描述，**只作为检索线索**，不直接下诊断。
- 为什么：中医四诊里舌诊占比高，纯文本问"舌淡苔白"其实是把图像先人工转写成文字，多模态能省这一步。
- 难点：① 红线——图片识别结论必须标注"仅供检索参考，不构成诊断"；② 图像描述要转成库里能命中的关键词（`meta_jsonb` 里没有舌象字段，需要建映射或加字段）；③ 成本——视觉模型按图计费，要加频控。

**(2) 简单 Agent 指令（快捷指令 / 斜杠命令）**
- 做什么：输入框支持 `/对比 麻黄汤 桂枝汤`、`/查证 太阳中风`、`/练习 太阳病 3 题` 这类结构化指令，**先由规则解析成确定的工具调用，再交给模型组织语言**。
- 为什么：高频问题是有限的几种（对比、查证、练题），让模型每次都自己规划既慢又不稳定；规则命中就直连工具，延迟能降一半。
- 难点：指令与自然语言要能共存（未命中斜杠就退回普通问答），以及指令的参数校验（方名不存在要明确报"查不到"，不能猜）。

**(3) 更多 tools**
- 现在 5 个：`search_formula` / `search_case` / `semantic_recall` / `graph_neighbors` / `syndrome_score`。
- 待补：`dosage_convert`（等 `dosage_rule` 表有数据，否则一定编剂量）、`quote_lookup`（按条文号查原文）、`formula_diff`（已经以独立端点实现，可包成工具）、`compare_formulas`（多跳对比，一次取两方组成做集合差）。
- 原则不变：**能确定性算的不交给模型**（组成差集、Jaccard、频次统计都是代码算）。

**(4) 对话内容引用进对话框**
- 做什么：选中正文/引用卡里的任意段落 → 右键或按钮"引用到提问"，把它作为带编号的上下文注入输入框（例如 `> 引用《伤寒论》35 条：太阳病，头痛发热…`），模型回答时必须针对该段作答。
- 为什么：用户常常想追问"这句话什么意思""这和 X 有什么关系"，重新描述一遍既麻烦又容易失真。
- 难点：① 引用段要带来源 id（`content_unit.id` / `classic_quote.id`），否则模型会自己"回忆"；② 上下文长度控制（引用 + 检索结果不能超预算）；③ 与 `citations` 编号体系统一，避免 `[1]` 出现两种含义。

**(5) 对话节点侧栏（会话树）**
- 做什么：右侧展示本次会话的"节点流"——每个问题是一个节点，追问形成子节点；点击任一节点可以回到该状态继续分叉（类似对话树），而不是线性历史。
- 为什么：辨证训练是树状的（"如果同时有烦躁呢""如果兼见口渴呢"），线性历史会把这些分叉压成一条，回溯时全丢。
- 难点：① 数据结构要从"消息列表"升级成"节点 + parent_id"；② 服务端要存树（现在 `agent_message` 是平铺的）；③ 前端布局要做自动排布（可复用已有 `graphLayout` 的思路）。

### 9.2 语料插拔（导入 / 删除）
见第六节。近期可做的最小闭环：**导入通道（文件上传 → 任务表 → 后台解析）+ 软删下架**，两者都需要先补 `case_record.node_id` 与 `:Book` 图谱节点。

### 9.3 学习模块优化

## 十一、高频问答（照着背）

**Q1：为什么用微服务？一个小项目拆 8 个服务不是过度设计吗？**
按读路径拆的（阅读/检索/图谱/练习/统计/身份），不是为了拆而拆：改检索 SQL 不用重启整个后端、压测能单点定位、Agent 可以独立扩容。代价是运维复杂度，所以反过来我们**没有**接 Nacos、没有 Dockerfile——单机阶段怎么省事怎么来，等有多机需求再补。

**Q2：Nacos 起了为什么不用？**
容器是留给部署阶段的，代码里没接：没有 nacos 依赖、没有 bootstrap.yml、没有 `@EnableDiscoveryClient`。网关和 Feign 都是 `http://localhost:8xxx` 静态直连。理由是单机开发静态地址排错最快；契约层已经把 `url` 做成可覆盖属性，接的时候只改配置。

**Q3：向量一定是 1024 维吗？能换模型吗？**
锁死 1024 维、`BAAI/bge-m3`。换 embedding 模型等于把所有 598 条单元重算一遍，而且要保证查询侧和入库侧同一模型——所以它不是"可调配置"，是数据契约的一部分，写在文档最显眼的地方。

**Q4：怎么保证模型不瞎编？**
三道：① 工具层面不挂 `dosage_convert`（没数据源，挂了必编剂量）；② 检索阈值 0.5 过滤 + 只允许引用命中编号，SSE 的 `done.illegalCitations` 会上报越界引用；③ 提示词之外还有产品层提示——涉及用药的页面固定显示"仅供学习参考，不构成处方建议"。

**Q5：为什么要手写 SVG 不用 ECharts？**
只有三种图（邻接图、雷达、散点地图），布局逻辑是自己的（后端给坐标/前端算邻居位置），引库反而要跟库的坐标系打架。手写之后布局变成纯函数，能直接单测（32 例测"节点在画布内、邻居不重叠、后端坐标不被重排"）。

**Q6：中文分词怎么办？**
`pg_jieba` 是条件安装，镜像默认没有，所以我们兜底建了 `jiebacfg`（`COPY OF simple`），并额外做了一条 **中文 2-gram 词项腿** + `pg_trgm` 模糊匹配来补分词不足。这条腿在混合检索里权重不小，是实测"分词不好也能搜到"的关键。

**Q7：为什么不用 LangGraph / AgentExecutor？**
我们要在决策轮去掉检索资料（带资料 + `tool_choice=required` 会让小模型撞满 max_tokens 返回空），还要控轮次与总耗时预算（3 轮 / 15s）、单工具超时重试。这些细节现成框架不好改，手写循环 80 行，能单测（`test_agent_loop.py` 21 例）。

**Q8：数据从哪来？洗了多久？**
原始是一本 400 页 docx。第一轮 ETL 以 `【问题】` 为锚点切块，导致锚点之外的内容（节首概述、病机论述、医案按语）整体丢失 9.7%。后来写补录脚本逐段比对 docx 与库内正文，把这 672 段补回来，并顺手把 78 个"表格"里的 2 个真表格结构化入库（其余 76 个是目录点线页）。细节在 `docs/A_docx正文补录操作手册.md`，含 14 条踩坑。

**Q9：系统现在能承受多少并发？**
没有做过正式压测，这是缺口。已知瓶颈位在：Agent 的限流是单进程内存窗口（60s/20 次）、BFF 用 Feign 同步转发无熔断、检索四腿是一次 SQL 里跑完（向量腿最重）。要压测应该先打 `/biz/search` 与 `/api/agent/ask/sync` 两个点。

**Q10：你怎么保证评分是公平的？**
评分是确定性算法不是模型判卷：药味用 F1（漏写和错写都要罚），三维加权 0.3/0.4/0.3。代码里如实标注了局限——辨证/治法分目前是字面重合度，不懂近义词，这是下一步要换成结构化证候要素比对的原因。

**Q11：前端 35 个路由，状态管理怎么做的？**
没用 Pinia（装了但 0 个 store）。跨页共享的只有"书单"和"登录用户"，用 composable 做模块级单例 + inflight 去重就够了；页面内状态用 `ref`。加 Pinia 只会多一层抽象。

**Q12：如果让你再做一遍，最先改什么？**
三件：① 先把 `case_record.node_id` 和 `:Book` 图谱节点补上（否则接第二本书就乱）；② 后端 CI 和 Agent 评测集先立起来（现在回归靠人）；③ `AskView` 接 SSE（后端已经写好了，前端还在用同步接口，白瞎了一半实现）。

## 十三、一句话总结（被问"这个项目的技术亮点是什么"）

> 不是"用了多少框架"，而是**每条技术选择都能对应一个具体问题**：四腿召回是因为中文分词不可靠、BFF 分区降级是因为首页聚合不能一处挂全白、章级懒加载是因为整章 489 KB 一拉就卡、规则评分是因为让模型判卷会不稳定、补录脚本是因为旧 ETL 的切分策略吃了 9.7% 的正文。
> 而缺口也清楚：注册中心、缓存限流、容器化交付、评测集都还没做，属于"知道该做、还没做"。
