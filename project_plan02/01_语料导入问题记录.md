# 01 语料导入问题记录（2026-11-11）

## 1. 事件经过

起因是一个提问：「导语料还要补代码吗？」。核查下来发现，这件事的风险不在代码，而在**导入方式**和**快照是否还有效**。

核查顺序（全程只读）：

1. `scripts/init-data.sh` 读脚本，确认导入分三步：导入快照 → 校验 5 个计数 → `build_graph.py` 建图。
2. `docker ps` 确认中间件：`herbmind-v2-pg` / `herbmind-v2-neo4j` / `herbmind-v2-redis` / `herbmind-v2-nacos` 全部 Up、healthy `[实核 2026-11-11]`。
3. `psql` 查库内各表计数。
4. 解析 `scripts/herbmind_data.sql` 的 `COPY ... FROM stdin` 块，统计快照里各表行数，与库对比。
5. `git check-ignore` 确认快照文件未入仓库。

## 3. 发现的问题

### P-01 全量快照只有「撞主键」和「DROP 重建」两条路，没有增量导入

- **现象**：`init-data.sh` 的导入方式是 `gunzip -c | psql`，SQL 里每行带固定 id（`COPY` 块，`INSERT` 语义）。库里已有同 id 行时违反唯一约束，`ON_ERROR_STOP=1` 导致整批回滚。
- **脚本自己的处理**：失败时提示加 `--reset`，即 `DROP SCHEMA public CASCADE; CREATE SCHEMA public;` 后重建。
- **影响**：想「只加新语料」这个诉求，现有工具做不到，只能全量推倒重来。

### P-02 快照已落后于库，`--reset` 会丢 309 条方剂组成

- **现象**：见 §2.1。
- **影响**：现在执行 `bash scripts/init-data.sh scripts/herbmind_data.sql --reset`，`formula_herb` 会从 1315 掉回 1006，补录成果被回滚。这是**真实的回退风险**，也是本次没有执行 `--reset` 的直接原因。
- **恢复手段**：理论上可重跑 `apply_supplement.py` 补回，但该脚本的输入依赖 `database/etl/data/` 下那三份 CSV，需先验证可重复执行（幂等）——目前**未验证**。

### P-03 `symptom` / `syndrome` 两表为空

- **现象**：快照和库里都是 0 条。
- **已知连带**：`formula_syndrome_rel`（方剂↔证型）、`case_symptom_rel`（医案↔症状）这类关联表即使有行也指向不存在的目标；训练/评分模块（`answer_score` 里的 `syndrome_score`）拿不到证型维度。
- **未确认**：这是「语料本身没抽这两类实体」还是「抽取后没落库」，需要内容域确认。**此处不下结论。**

### P-04 导入后的校验只看 5 个计数，查不出结构性问题

- **现象**：`init-data.sh` 第 2 步只打印 `formula / case_record / classic_quote / content_unit / 向量` 五个数，没有断言、没有阈值，人眼比对。
- **影响**：以下问题都会被「验证通过」：方剂有 `formula` 行但没有 `formula_herb` 组成（对应 `no_herb_formulas.csv` 的那批）、`content_unit.ref_id` 指向已删除的目标、`relation` 里 `to_id` 悬空。数量对了不代表数据能用。

### P-05 快照靠私下分发，文件名不带版本

- **现象**：`herbmind_data.sql` 固定文件名（`.gitignore` 第 20 行忽略），无日期、无版本号、无清单。
- **影响**：拿到一份快照无法判断它是哪天的基线、比库里新还是旧、缺哪些表。本次是靠文件时间戳 + 逐表计数才反推出「10-12 基线 + 10-26 补录」这个事实。


## 5. 本次的结论（给非技术同事的说法）

- 库里的语料是**齐的**，不用重新导，直接起后端和前端就能用。
- 「撞主键」不是说库里数据有问题，是说**重复导入同一个文件会被数据库拦住**——这其实是保护机制。
- 现在这份快照文件是**旧版**，别拿它当唯一真源；要重装数据的话，得先把补录的 309 条方剂组成考虑进去，否则会丢。

## 6. 附：验收时顺带发现的问题（2026-11-11 起服务阶段）

### P-06 `scripts/run-dev.ps1` 的 `--server.port` 未生效，五个服务抢同一个 8080

- **现象** `[实核 2026-11-11]`：执行 `run-dev.ps1` 后，8082/8083/8086/8090 全部 FAIL，只有 8080 OK。日志显示 `svc-catalog` 起在了 **8080**（本该 8082），其余四个报 `Web server failed to start. Port 8080 was already in use.`
- **根因**：脚本第 52 行 `$argList = @("-jar", $jarPath, "--server.port=" + $s.Port)` 经 `Start-Process -ArgumentList` 传给 JVM 时端口参数实际未到达，五个服务一律回落到 `application.yml` 的默认值。
- **临时绕过**（本次采用）：改用 `start /b java -jar <jar> --server.port=<端口>` 逐个显式启动，五个服务全部正常监听。
- **影响**：任何人直接跑 `run-dev.ps1` 都只能起一个服务，且起错的那个占着网关端口 8080，前端会打到 catalog 而不是网关。`run-dev.sh`（nohup 版本）未验证是否有同样问题。
- **状态**：未修改脚本（跨域公共脚本，改动须先与域负责人确认）。

### P-07 启动脚本只起 5 个服务，实际有 8 个模块

- `backend/` 下共 8 个可运行模块：`svc-identity`(8081) / `svc-catalog`(8082) / `svc-search`(8083) / `svc-training`(8084) / `svc-graph`(8085) / `svc-insight`(8086) / `herbmind-bff`(8090) / `herbmind-gateway`(8080)。
- `run-dev.ps1` / `run-dev.sh` 只起 catalog / search / insight / bff / gateway 五个，**漏了 identity / training / graph** `[实核 2026-11-11：各模块 application.yml 的 server.port]`。
- 其中 `svc-graph`(8085) 是 Agent 的依赖（Agent 启动日志：`graph=http://localhost:8085`），不起它 Agent 的图谱类工具全部落空。
- 本次已手动补起这三个，8 个服务 + Agent 全部监听正常。

### P-08 的根因（两个叠在一起）

1. **`_question_of` 取错了问题**：它用 `content.split("【问题】", 1)[1]` 取**第一个**标记之后的内容，而库里的医案/方剂正文自带「【问题】1.某某如何鉴别?」这类小标题（射干麻黄汤、麻黄连翘赤小豆汤的按语里都有）。结果「问题」拿到的是整段【资料】。连带让 `needs_tool_evidence` 也误判。
2. **决策轮把资料一起发给了模型**：带上 5 条召回资料 + `tool_choice="required"`，Qwen2.5-7B 会顺着资料写长文直到撞满 `max_tokens`；此时硅基流动返回 **HTTP 200 但 `choices: []`**（`completion_tokens` 恰好等于 800，改成 2000 就是 2000），LangChain 取 `llm_result.generations[0][0]` → `IndexError: list index out of range`。

**证据（原始 HTTP 矩阵测试，同一问句）**：

| 输入 | tool_choice | choices | completion_tokens | 结果 |
|---|---|---|---|---|
| system + 问题 | required | 1 | 28 | `finish=tool_calls`，正常调工具 |
| system + 问题 | auto | 1 | 26 | `finish=stop` |
| 仅问题 | required | 1 | 20 | `finish=tool_calls` |
| **资料 + 问题（完整）** | required | **0** | **800** | 空 choices → IndexError |
| 资料 + 问题（完整） | required，max=2000 | **0** | **2000** | 同上，加预算只是更慢 |

**改法**：

- `_question_of` 改为 `rsplit("【问题】", 1)`，取**最后一个**标记后的内容；
- 新增 `_decision_messages()`：决策轮只发 system + 问题，**不带【资料】**（决策轮的正文本来就不采用，最终回答另起 astream 生成，删资料零损失）；
- `stream_tool_loop` 同时维护两份消息：`current`（完整，含资料 + 工具结果，供最终生成）与 `decision`（精简，供模型决定调不调工具），工具结果同时追加到两份；
- 决策失败的日志加 `exc_info=True`，以后能看到完整栈。

**修复后实测**：`toolCalls=[{search_formula, {"name":"麻黄汤"}, ok=true, hit=true, count=8, ms=109}]`，`toolsMs` 19806 → 2457ms，`POST /ask/sync` 22.6s → 4.0s，答案仍为「麻黄汤的组成是麻黄、桂枝、杏仁、甘草 [1]」，`degraded=false`。

**回归用例**（`agent/tests/test_agent_loop.py` 新增 3 条）：取最后一个【问题】标记、决策轮不含资料、最终生成仍保留资料。全量单测 202 → **205 passed**。
