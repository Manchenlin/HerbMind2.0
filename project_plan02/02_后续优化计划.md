## P0-1 建立新基线快照

**做什么**：把当前库（10-26 补录后的状态）导出为新基线，作为以后分发的唯一真源。

```bash
docker exec herbmind-v2-pg pg_dump -U postgres -d herbmind --no-owner --no-acl \
  | gzip > herbmind_data_20261111.sql.gz
```

**验收标准**：

- 新快照 `formula_herb` 行数 = 1315，`formula` = 245，`content_unit` = 535（含向量 535）。
- 在干净库上「`--reset` + 导入新快照」跑通一次，计数与现库逐表相等。
- 旧文件 `scripts/herbmind_data.sql` 保留但**改名标注过期**（如 `herbmind_data_20261012_过期.sql.gz`）或直接删除——删除属于红线操作，须先确认。

**注意**：快照文件按 `.gitignore` 第 20 行不入仓库，靠私下分发，所以「新基线出来后，通知所有持有旧文件的人换掉」这一步要显式安排，否则旧文件会继续流动。

## P0-2 导入前安全检查

**做什么**：让 `init-data.sh` 在破坏性动作前强制过关。

**三项具体改动**：

1. `--reset` 执行前自动 `pg_dump` 备份到 `database/backup/<时间戳>.sql.gz`，并在屏幕上打印备份路径。
2. 执行前打印「将丢失什么」：当前各表行数 vs 快照各表行数，差值非零的行标红提示（例如「`formula_herb`：库内 1315 → 快照 1006，将丢失 309 行」）。
3. 新增 `--dry-run`：只做上面第 2 步的比对，不动库。

**验收标准**：对当前库跑 `--dry-run`，能准确报出 `formula_herb` 会丢 309 行；对当前库跑 `--reset` 会先落一份备份文件再继续。

## P1-1 增量导入

**为什么需要**：现有流程只有「全丢重来」，而实际场景多是「手上又多了 50 个医案，加进去」。全量重装的代价是：所有用户产生的数据（笔记、训练记录、收藏、讨论）一起被清空——这是最容易被忽略的损失。

**三个方案，各有代价**：

| 方案 | 做法 | 好处 | 坏处 |
|---|---|---|---|
| A. 全量重装 + 事后补录（现状） | `--reset` 后重跑 `apply_supplement.py` 等补录脚本 | 改动最小，逻辑最简单 | 用户生成数据全丢；补录脚本必须幂等且齐全，漏一个就少一块 |
| B. `COPY`→`INSERT ... ON CONFLICT DO NOTHING` 转换 | 把快照按表转成带 `ON CONFLICT` 的插入，跳过已存在主键 | 真增量、可重复执行、不动用户数据 | 需要处理列顺序与外键顺序；快照体积大时逐行插入较慢 |
| C. 分域导入工具（按 `unit_type` / `book_id` 切） | 按内容域划分，只导指定范围 | 最贴合「按书导入」的业务形态（当前分支 `feat/import-case-book` 正在做的事） | 工作量最大，需要先定义域边界 |

**推荐**：先做 **B**，作为通用安全网；C 等 `feat/import-case-book` 的分书导入方案定型后再决定是否抽象。理由是 B 不依赖业务分类、能立刻覆盖「重复导入不报错」这个最高频场景，且不会误伤用户数据。

**验收标准**：

- 对已导入过的快照再跑一次 B，退出码 0，各表计数不变（幂等）。
- 对只含新行的快照跑 B，新行全部插入，旧行不被修改。
- 用户生成表（`user_note` / `training_*` / `user_favorite` / `discuss_*` / `learning_*` / `wrong_book` / `recite_record`）在任何情况下不被删除。

## P1-2 数据体检脚本

**做什么**：把「数量对」升级成「结构可查」。建议一次体检输出以下项，任一不通过即退出码非 0：

1. 全表计数（不是只 5 个表）。
2. 方剂无组成：`formula` 中没有对应 `formula_herb` 的行数（当前已知存在这类方剂，见 `no_herb_formulas.csv`）。
3. 悬空引用：`content_unit.ref_id` 指向的 `formula` / `case_record` / `classic_quote` 是否存在。
4. 关联表目标缺失：`formula_syndrome_rel` / `case_symptom_rel` / `case_quote_rel` 的目标行是否存在。
5. 向量覆盖：`content_unit` 中 `embedding IS NULL` 的行数（当前为 0）。
6. 维度断言：`vector_dims(embedding) = 1024` 全部成立（向量空间锁死 1024 维 / `bge-m3`）。
7. 生成列未被 ORM 写入的旁证：`content_unit.search_tsv` 非空行数 > 0。

**验收标准**：脚本对当前库跑一遍，输出上述 7 项；人为把一条 `content_unit.ref_id` 改坏后能报出来。

**分工提示**：这个脚本只读库、不改库，属跨域工具，建议放 `scripts/` 由统筹方维护，输入由各域提供口径。

## P1-4 修 Agent 工具取证 IndexError

**现象**（详见 `01` P-08）：命中「清单类问法」时强制 `tool_choice=required`，随后解析模型响应下标越界，日志 `第 1 轮工具决策失败，停止取证：list index out of range`，`toolCalls=[]`，`toolsMs` 14~20 秒。

**验收标准**：

- 问「麻黄汤的组成是什么？」，日志不再出现该 WARNING。
- `toolCalls` 非空，且调用的工具参数可在 `agent_tool_call` 表查到。
- 同一问句端到端耗时从 15~21 秒降到 5 秒内（检索 ~0.25s + 生成 ~1.3s + 工具决策）。
- 加 1 条回归用例：模型返回空 `choices` 时不崩、降级为不取证（`degraded` 标记如实反映）。

**为什么优先**：这是当前问答链路上唯一的实际 bug，且直接决定「带工具的多轮能力」能否成立。

## P1-6 修启动脚本

两处一起改：

1. `run-dev.ps1` 的端口参数未生效（现象见 `01` P-06）。改法二选一：
   - 用单个字符串传参：`-ArgumentList "-jar `"$jarPath`" --server.port=$port"`；
   - 或直接 `Start-Process cmd -ArgumentList "/c java -jar ... --server.port=X > log 2>&1"`。
2. 服务清单从 5 个补到 8 个：加入 `svc-identity`(8081) / `svc-training`(8084) / `svc-graph`(8085)。`svc-graph` 尤其不能漏——Agent 依赖它。

**验收标准**：干净环境（全部 java 进程停掉）执行一次启动脚本，8 个端口全部 LISTENING，无需手工补。

## P2 其它

- **P2-1 命名规范**：`herbmind_data_<YYYYMMDD>.sql.gz` + 同目录 `MANIFEST.md` 记录「导出时间 / 各表行数 / 相比上一版增减 / 谁导出」。目的是让下一份快照到手时**不用再靠逐表计数去反推它比库里新还是旧**。
- **P2-2 `--verify-only`**：只跑计数与体检，不导入，给 CI 或改动后自查用。
- **P2-3 补录脚本幂等性**：`apply_supplement.py` 能否重复执行而不产生重复行，目前未验证；这直接影响方案 A（全量重装）是否安全。

## 需要决策的事项（等确认）

3. 增量导入选 A / B / C 哪个方案先落地？
4. `symptom` / `syndrome` 的补齐由谁负责（域1 还是域3）？
5. 旧快照 `scripts/herbmind_data.sql` 是否删除（红线操作，需明确同意）。

## 不建议做的

- **不建议在生产/演示库上直接试 `--reset`**：没有备份机制前，一次误操作就要重跑全部 ETL。
- **不建议为了让导入「不报错」而给 SQL 加 `ON CONFLICT DO NOTHING` 了事**：那会掩盖「快照是旧版」这个真正的问题，让数据静默停留在旧状态。B 方案的前提是先有 P0-1 的新基线。
- **不建议把快照纳入 git**：8.9 MB 仅当前规模，全量与增量交替还会继续涨，`.gitignore` 的现有策略合理。
