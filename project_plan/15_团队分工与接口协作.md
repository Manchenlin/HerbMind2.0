## 1. 背景与分工原则

**团队画像**：3 人；其中 **1 人纯前端**，后端（Java）与 AI（Python）需边学边做。
**团队目标**：**希望每个人都能接触到前端和后端**（学习优先）。

**结论**：采用 **纵向域切** —— 每人端到端负责一个业务域（**后端服务 + 前端页面**）。

| 方案 | 结论 |
|---|---|
| 层切（前端 / 后端 / AI） | ❌ 层切下"纯前端那位永远碰不到后端"，**与"人人接触前后端"的目标冲突** |
| **域切（本次）** | ✅ 每人一域、端到端全栈，**人人都有前后端** |

**代价与前提**：每人学习面变宽 → 必须靠 **阶段 0 三人合力搭地基 + 契约冻结 + mock** 来缓释（见 §3/§6）。

## 2. 三域与三人

| | **域1 · 内容域（读）** | **域2 · 成长域（练）** | **域3 · 智能域（问）** |
|---|---|---|---|
| **成员** | **A（原纯前端）** | B | C |
| **后端服务** | catalog / search / insight | identity / training / **BFF** | agent(Python) / graph / governance |
| **数据** | book / book_node / content_unit + **ETL / 向量** | app_user / training_* / + **评分算法** | Neo4j / agent_* + **建图脚本** |
| **前端页面** | 书架·导入 · 典籍 · 检索 · 科研 + **首页**（**13**） | 练习 · 我的 · 讨论 · 登录（**14**） | 图谱 · 问答 · 治理（**8**） |
| **主要习得** | SQL · 全文检索 · ETL | 业务逻辑 · 评分 · 表单流 | Python · LLM · 图 · 流式 |
| **兼** | — | **BFF / 集成负责人** | 云 API key 管理 |

> **页面口径**：上表为 [03](03_信息架构与页面清单.md) 的**规划页数**（35 + 首页/404）；原型 21 页是子集，勿混用。
> **配平说明**：`insight` 归域1（偏数据）、`BFF` 归域2（薄聚合层）—— 避免域3 一人又扛 Java 又扛 Python 又扛 BFF。
> **纯前端成员（A）放域1**：该域后端是纯 CRUD + SQL，**最容易入门**；且前端页最多，能立刻发挥。

**每人都会做这两件事**：① 写自己域的后端接口（Java，域3 另加 Python）；② 写自己域的前端页面（Vue）。

## 3. 阶段 0：三人合力（打地基 + 冻结契约）

> 域切比层切**更需要**这一步：三个人都会碰后端基础设施，地基不一起搭就会出现三套写法。

**产出（一次性，之后各自抄模板）**：
1. **接口文档冻结** —— `09_API契约清单.md` 补全字段表与示例（见 §4）。
2. **数据库** —— DDL（book / book_node / content_unit + 三域表）+ 初始化脚本。
3. **骨架** —— 网关 + BFF 空壳 + **一个样例服务**（catalog）+ 前端框架。
4. **一条端到端样例链路** —— 前端页 → BFF → 样例服务 → PG，**跑通**（所有人的模板）。
5. **一键包** —— `docker-compose.infra.yml` + `database/` 脚本 + 三行命令 README。

## 4. 接口文档规范（★ 最重要的一环）

> 契约先于代码：**先改 `09` → 群内通知 → 再写代码**；契约是**唯一事实源**，改动需三人同意并记录。

统一约定（`R<T>` / `PageResult` / **JSON camelCase、DB snake_case** / ISO 8601 / 字符串 ID / Bearer 鉴权）见 [09 §0](09_API契约清单.md)；每个接口必须写全 8 项；**三域各一个打样接口**见 [09 §13](09_API契约清单.md)。

## 4.1 前端视觉基线（★ 前端必须遵守）

**唯一视觉标准 = `project_plan/prototype/`**（21 个 HTML + `assets/theme.css`）。三个人做的页面必须长一样，否则拼起来就是三个网站。

| 要求 | 具体做法 |
|---|---|
| **样式** | 只用 `frontend/src/styles/theme.css`（**已从原型移植**）里已有的 class：`.topbar / .hero / .card / .grid / .stat / .chip / .rowitem / .cite / .pill-tabs / .auth / .field / .btn` … **不要另起一套颜色/圆角/间距**；**不引入 Element Plus** 等 UI 库 |
| **布局骨架** | 已实现：`AppHeader`（顶栏 = 品牌 + 8 项导航 + 语料切换器 + 登录）+ `<main class="wrap">` + `footer`，直接用 |
| **对照实现** | `frontend/src/router/index.ts` 中未实现的页面会走**占位页**（`ComingSoonView`），它会**直接显示「负责人 + 照 `prototype/xxx.html` 做」** |
| **流程** | 新增页面：先在 [03](03_信息架构与页面清单.md) 登记 → 照对应原型页写 → 把路由从"占位"换成真实组件 |
| **数据** | 一律走 `/api/biz/**`（经 `src/api/request.ts`，已剥 `R<T>` 外壳）；字段 camelCase（`nodeType`） |

> **为什么这样做**：原型是"视觉合同"。有了 `theme.css` + 占位页指引，三个人**不用靠口头对齐样式，照着复制就不会跑偏**。

## 5. 环境与数据准备（不需要人人从零准备）

| | 要不要每人准备 | 怎么准备 |
|---|---|---|
| **Docker Desktop** | ✅ 每人装一次 | 不需要每人研究 Dockerfile |
| **中间件** | ❌ 不重复造 | **一套 `docker-compose.infra.yml`**，三人共用 |
| **数据**（语料 + 向量 + 图谱） | ❌ 不手工配 | **脚本化 + 种子**，跑脚本自动生成 |

**三人最小环境**：

| 成员 | 中间件 | 语言 / IDE |
|---|---|---|
| **A · 域1** | PG(+pgvector/pg_jieba)、Neo4j、Redis | IDEA（Java）+ Vite/Node（前端） |
| **B · 域2** | PG、Redis | IDEA + Vite/Node |
| **C · 域3** | PG、Neo4j、Redis、Nacos | IDEA + **PyCharm（conda `herbmind`）** |

> **三人都有前端** → 三人都要 Node/Vite 环境。
> 数据要点：**向量（embedding）与 Neo4j 图数据由域1 跑一次生成后共享**，其他人直接导入，**别三人各烧一遍云额度**；大文件走网盘 / Git LFS。
> 简化建议：本地开发可用 `local` profile 静态直连，Nacos 留到集成日。

## 6. 协作机制

| 项 | 约定 |
|---|---|
| **契约先行** | `09` 唯一事实源；改契约需三人同意 + 变更记录 |
| **前端不被阻塞** | 按契约生成 **mock**，各自独立开发 |
| **Git** | `main` 保护；每人 feature 分支 → PR；**契约文件改动需 3 人 review** |
| **横切共同维护** | `common` / `contract` / 网关 / `09` 契约 —— 谁改都要三人 review |
| **集成** | 每周一次：合并 + 跑通端到端样例链路 |
| **沟通单位** | 以**域**为单位同步进度（A=内容域、B=成长域、C=智能域） |

---

## 7. 风险与降配

| 风险 | 应对 |
|---|---|
| **人人全栈 → 学习曲线陡** | 阶段 0 的"样例链路"当模板逐段抄；每人只管自己域 |
| 契约漂移（三人都改接口） | `09` 冻结 + 变更走 review |
| 后端整体偏弱 | **架构降配**：一期先做 **3 服务**（内容、用户、agent）+ 单体 BFF |
| 数据不一致 | 全靠脚本化种子 + ETL 统一产出 |
| 云 API 额度 | 域1 统一产出 embedding/图数据；C 管理 key |
