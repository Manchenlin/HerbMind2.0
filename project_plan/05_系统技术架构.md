## 2. 微服务清单

| 服务 | 端口 | 职责 | 主要数据 |
|---|---|---|---|
| `herbmind-gateway` | 8080 | 统一入口、JWT 鉴权、路由、限流；只暴露 `/api/biz/**` 与 `/api/agent/**` | 无 |
| `herbmind-bff` | 8090 | **BFF 编排**：按页面聚合多服务数据，统一 `R<T>` 返回 | 无（可缓存） |
| `svc-identity` | 8081 | 用户、角色、收藏、笔记、讨论 | app_user / favorite / note / discuss |
| `svc-catalog` | 8082 | **语料管理（book）** + 典籍、方剂、案例、条文、药味 内容读写 | book/book_node/classic/formula/case/quote |
| `svc-search` | 8083 | 多维检索：pg_jieba 全文 + pgvector 向量混合召回 + 分面 | 读 catalog；content_unit |
| `svc-training` | 8084 | 练习会话、答题、评分、学习档案、错题本、背诵 SRS | training_* / learning_* / wrong_book |
| `svc-graph` | 8085 | Neo4j 图谱查询：子图、多跳、路径、相似度地图数据 | Neo4j |
| `svc-insight` | 8086 | 科研统计、挖掘、导出（CSV/JSON/GraphML） | 聚合读 |
| `svc-governance` | 8087 | 校验流转、复核工单、OCR 疑点、审计 | content_review / issue / audit_log |
| `herbmind-agent` | 8091 | **Python Agent 服务**（FastAPI + LangChain 1.x） | agent_conversation / agent_message / agent_tool_call |
| 中间件 | PG 5432 / Neo4j 7687·7474 / Redis 6379 / Nacos 8848 | — | — |

### 2.1 语料管理与插拔（新增 · 见 [14](14_插拔式书籍扩展方案.md)）

- **语料可插拔**：以 `book` 为顶层语料注册表（书类型：方证/本草/药品/医案），`book_node` 为通用目录骨架，`content_unit` 为跨书统一检索入口。
- 新增一本书 = **注册 + 跑通用导入器**（栏目规则模板 + 字段→本体映射），**不改服务、不改表**。
- `svc-catalog` 承担语料管理；`svc-search` / Agent 检索面向 `content_unit` 统一召回。
- **服务拆分决策**：一期 **不拆** `svc-corpus`，语料管理留在 `svc-catalog`（内部以 `corpus` 包划分 `book / book_node` 与内容表边界）；当语料规模或导入并发增大时，再物理拆出独立 `svc-corpus`。

## 3. BFF 设计（面向页面聚合）

BFF 是**前端唯一入口**，按"一个页面一个接口"聚合。示例：

| BFF 端点 | 聚合来源 | 返回 |
|---|---|---|
| `GET /api/biz/home` | catalog + search + graph | 数据概览 + 今日方证 + 图谱预览 |
| `GET /api/biz/formula/{id}/page` | catalog + graph + identity | 方剂 + 条文 + 案例 + mini 图 + 是否收藏 |
| `GET /api/biz/me/dashboard` | training + identity | 学习概览 + 雷达 + 打卡 |
| `GET /api/biz/admin/overview` | governance + insight | 治理总览 |

## 4. 调用规约

| 编号 | 规约 |
|---|---|
| R1 | **业务服务零横向调用**：svc 之间不互调，跨域聚合统一由 BFF 完成。 |
| R2 | **R8 隔离**：网关只暴露 `/api/biz/**`、`/api/agent/**`；`/internal/**` 仅供服务间调用，不对外。**免鉴权白名单**：`/api/biz/user/login`、`/api/biz/user/register`、`/api/agent/health`。 |
| R3 | **R5 上下文透传**：网关校验 JWT 后，以请求头 `X-User-Id / X-User-Role / X-User-Name` 向下游透传。 |
| R4 | **R6 BFF 薄层**：BFF 只做编排与聚合，不写业务规则。 |
| R5 | **统一响应 `R<T>`**：`{code, msg, data}`；异常由全局处理器统一包装。 |
| R6 | **契约先行**：DTO 与 Feign 接口集中放 `backend/herbmind-contract/`，各 svc 只依赖自己那份契约模块。 |
| R7 | **OpenFeign 4.x**：禁类级 `@RequestMapping`，用 `@FeignClient(value="svc-x", path="/api/biz/x")`。 |
| R8 | **Agent 独立**：`herbmind-agent` 是 Python 服务，注册 Nacos，经网关路由 `/api/agent/**`；不与 Java 服务共用进程。 |

## 4.1 路由分层（方案 A · 对外 / 对内）

| 前缀 | 归属 | 说明 |
|---|---|---|
| `/api/biz/**` | **BFF 独占** | 前端唯一业务入口（含 login/register 白名单） |
| `/api/agent/**` | **Agent 独占** | 前端智能入口 |
| `/internal/**` | **各 svc 独占** | 服务间调用，**不进网关** |

> **强规约**：各 svc **不得再暴露 `/api/biz/**`**——`/api/biz/**` 由 BFF 独占，消除"网关不知路由给谁"的歧义。

## 4.2 服务内部结构规范（强制）

```
svc-xxx/src/main/java/com/herbmind/svcx/
├── controller/   # 仅接收 /internal/**；取 X-User-Id 等头
├── service/      # 业务逻辑
├── mapper/       # MyBatis-Plus
├── entity/       # 表映射（OffsetDateTime；GENERATED 列不映射）
├── dto/          # 请求 / 响应 DTO
├── convert/      # entity ↔ contract 转换
└── XxxApplication.java   # @ComponentScan("com.herbmind.svcx","com.herbmind.common")
```

## 4.3 数据归属与同步

| 域 | 归属 svc | 关键表 |
|---|---|---|
| 语料 / 内容 | svc-catalog | book / book_node / classic / formula / case / classic_quote |
| 检索索引 | svc-search（**只读**） | content_unit（**由 ETL 写**，search/agent 只读） |
| 用户 / 社区 | svc-identity | app_user / favorite / note / discuss |
| 练习 / 档案 | svc-training | training_* / learning_* / wrong_book |
| 图谱 | svc-graph | Neo4j（由 ETL 派生） |
| Agent | herbmind-agent | agent_conversation / message / tool_call |
| 治理 | svc-governance | content_review / issue / audit_log |

> **同步策略（明确）**：内容变更 **不实时同步**索引与图谱；由 `database/etl/` **定时或手动**重建 `content_unit` 与 Neo4j（`graph_synced` 标记）。v1 **不引入消息队列**。

## 4.4 前端登录态约定

- 登录成功 → 保存 `token`（`localStorage`，Pinia 同步持有）；
- 所有 `/api/**` 请求头带 `Authorization: Bearer <token>`；
- `401/403` → 清 token + 跳 `/login`；前端**不解析 JWT**；
- 免 token 白名单：`/api/biz/user/login`、`/api/biz/user/register`、`/api/agent/health`。

| 层 | 技术 |

## 6. 开发运行方式（★ 本地 IDE，不容器化应用）

| 组件 | 怎么跑 | 工具 |
|---|---|---|
| Java 微服务 | 各服务以 Spring Boot 主类本地启动（`local` profile；端口见上表） | **IDEA** 打开 `backend/pom.xml` |
| Python Agent/RAG | `uvicorn app.main:app --port 8091`，解释器 = **conda env `herbmind`** | **PyCharm** 打开 `agent/` |
| 前端 | `npm run dev`（Vite，proxy `/api → http://localhost:8080`） | 终端 / WebStorm |
| 中间件 | **Docker Desktop 仅跑基础设施**：PG / Neo4j / Redis / Nacos（`docker-compose.infra.yml`） | Docker |
| 业务应用容器化 | ❌ 开发期**不做**（改代码即重启） | — |
| 部署（Docker/虚拟机） | **开发完成后再定，最终由用户决定** | — |

**最小启动顺序**：① `docker compose -f docker-compose.infra.yml up -d`（中间件）→ ② IDEA 启动 Nacos 依赖的服务（先 identity/catalog）→ ③ PyCharm 启动 agent → ④ 前端 `npm run dev`。

## 7. 部署方案（备用，非开发期）

当决定上线时，提供 `docker/` 全栈 compose：Nginx + Gateway + BFF + 7 svc + agent + PG + Neo4j + Redis + Nacos，一键起。开发阶段不启用。
