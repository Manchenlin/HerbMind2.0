> 把《软件工程导论》的主要知识点映射到本项目的文档和实际分析动作，避免“文档写了但不知道为什么写”。

## 2. 关键概念在本项目中的含义

### 2.1 软件生命周期

从立项、需求、分析、设计、实现、测试、部署到维护的完整过程。本项目当前处在**问题定义阶段**，不把现有实现当作系统生命周期的起点。

### 2.2 需求

需求不是页面清单，也不是技术方案，而是系统为了解决问题必须提供的条件和能力。例如：

- 需求：学习者应能从一个方剂查看其组成药味和原文出处。
- 不是需求：使用 Neo4j 存储方剂关系。

后者是可能的设计方案，必须由需求和质量约束推导。

### 2.3 功能需求与非功能需求

- **功能需求**描述系统做什么。
- **非功能需求**描述系统做得怎么样，例如性能、安全、可用性、可维护性。
- 非功能需求必须有度量方式，否则无法验收。

### 2.4 用例

用例表示一个参与者为达成目标与系统发生的一组交互。用例不是单个页面，也不是数据库操作。

### 2.5 软件体系结构

体系结构是系统的高层结构，包括主要组成部分、职责、关系以及约束。架构设计要说明为什么这样划分，而不是只画一张模块图。

### 2.6 模块化

追求高内聚、低耦合。一个模块应围绕清晰的职责组织，接口尽量稳定，内部实现可以变化。

### 2.7 需求追踪

从需求来源一直追踪到设计、实现和测试，证明每个关键需求都有人负责、有设计承接、有测试验证。

### 2.8 软件质量

质量不只是“没有 bug”，还包括功能正确性、可靠性、易用性、性能、安全性、可维护性和可移植性。不同质量属性可能需要冲突取舍。

### 2.9 配置管理

对文档、代码、图表、测试用例等配置项进行标识、版本控制、变更控制和状态记录，保证团队使用的是同一版本。

### 2.10 验证与确认

- **验证（Verification）**：我们是否正确地构建了系统。
- **确认（Validation）**：我们是否构建了正确的系统。

需求评审、设计评审、测试和用户验收分别承担不同层次的验证与确认。

## 3. 课程方法与本项目动作的对应

| 课程活动 | 本项目中的具体动作 | 证据放在哪里 |
|---|---|---|

| 需求分析 | 建立用例、领域模型和流程模型 | `docs/04` |

| 详细设计 | 设计接口、数据、状态和异常处理 | `docs/05`、`docs/06` |

## 4. 常见误区

| 误区 | 问题 | 正确做法 |
|---|---|---|
| 把页面当需求 | 页面只是实现形式，不能说明为什么需要 | 先写用户目标和验收条件 |
| 把技术栈当设计 | 技术选型不等于结构设计 | 先划分职责和接口，再选技术 |
| 只画图不解释 | 图无法表达取舍和约束 | 每幅图说明目的和结论 |
| 非功能需求写口号 | “高性能”无法验收 | 给出场景、指标和测量方法 |
| 需求没有编号 | 无法追踪和变更 | 使用稳定 ID |
| 测试只看正常流程 | 忽略异常、边界和权限 | 从风险和失败模式设计用例 |
| 文档互抄 | 同一事实出现多个版本 | 指定单一事实源 |
| 先写实现再补理由 | 设计变成事后解释 | 先定义问题、约束和方案比较 |

## 5. 复习检查问题

每完成一个阶段，用以下问题检查是否真正理解：

1. 这个阶段回答了什么工程问题？
2. 产物给谁看，读者需要用它做什么决定？
3. 哪些内容是事实，哪些是假设？
4. 如果上游需求改变，哪些下游内容会受影响？
5. 有没有无法验证的表述？
6. 有没有用技术方案替代需求分析？
7. 图表是否能支持一个明确结论？
8. 这份文档和上一份文档的术语、编号是否一致？

## 6. 使用方式

- 正式文档不照搬本知识地图的教科书语言。
- 写作前查本表确认该章节要解决的工程问题。
- 用户复习课程时，可从“课程主题 → 项目落点 → 产物”反向检查。
- 新增重要课程概念时，在本文件补充，而不是散落在对话里。
