## 1. 文档信息

### 1.1 目的

本文档把 `docs/01` 的问题与目标、`docs/02` 的可行性结论与范围收缩，转成可验收的需求：每条需求有编号、有来源、有验收条件，能被 `docs/04`～`docs/08` 逐条引用。

本文档按需求分析的四项任务组织：**① 确定综合要求**（八类，§7）、**② 分析数据要求**（§8）、**③ 导出逻辑模型**（§9）、**④ 修正开发计划**（§10）。前两项产出需求的正式表述，第三项是需求边界的交叉校验，第四项是需求结论对进度与范围的反馈。

本文档不描述界面布局，不规定数据库结构，不做模块划分与接口设计——那些属 `docs/04`～`docs/06`。

### 1.2 范围

覆盖：需求来源与获取方法（含情景分析）、角色与使用场景、用例清单、功能需求与验收条件、八类综合需求与度量、业务规则与设计红线、数据要求与数据词典、逻辑模型概览、修正开发计划、假设与范围外事项、需求追踪矩阵初稿。

不覆盖：界面视觉设计、技术选型、数据表结构与索引、测试用例正文（`docs/08` 写）。§9 的逻辑模型只到"需求边界可校验"的粒度，细化表达以 `docs/04`、`docs/06` 为准（分工见 §9.4）。

### 1.3 读者对象

`docs/04`～`docs/10` 的编写者、课程评审者、实现者、内容维护者。

### 1.4 术语与缩略语

沿用 `docs/01` §1.4 的定义，另补充需求层术语：

| 术语 | 说明 |
|---|---|
| 内容单元 | 系统内可检索、可引用、可定位的最小内容记录，是需求层的操作对象 |
| 段落性质 | 内容单元的来源性质标记，取值：典籍原文／注释／教学论述／医案／其他（非正文）。仅"典籍原文"可作判据与出处；"其他"指序跋、凡例、附录、编校说明等不参与检索与引用的正文外内容 |
| 判据字段 | 可用于机器判定的字段，如方名、药味组成、条号。缺失时该记录不参与出题 |
| 显示值 | 按底本原样呈现的文本，不得改写 |
| 归一值 | 由显示值经确定性规则生成的检索用文本（繁简、异体字、标点统一），不参与展示 |
| 校勘记录 | 记录显示值与归一值差异及其依据的独立记录 |
| 出处块 | 输出内容旁统一呈现的定位信息：书名、篇名、条号（可得时）、原文片段 |
| 验收条件 | 一条需求可被判定为"已满足"的客观标准，须可执行、可复现 |
| 追踪矩阵 | 需求 → 设计 → 实现 → 测试的对应表，任一段为空即为断链 |

"显示值／归一值"是同一段文字的**两份存储**，不是两个概念：

| 场景 | 显示值（底本原样，用于展示） | 归一值（按规则改写，只用于检索） |
|---|---|---|
| 底本用繁体，用户输入简体 | 黃連 | 黄连 |
| 用户多打空格 | 桂枝汤 | 桂枝汤（空白折叠后） |
| 底本用异体字 | 白朮 | 白术 |

两条纪律：**归一值不得出现在界面上**（出现即等于改了底本，违反 BR-03）；**归一值必须可由显示值重新算出**（同规则跑两遍结果一致，NFR-06），所以它不作为权威数据单独维护，规则错了可以整批重算。

## 2. 需求来源与获取方法

### 2.1 需求来源与证据等级

本项目没有做真实学习者访谈与任务观察（`docs/01` §5.2 已承认）。因此每条需求都必须标出证据等级，避免把假设写成事实：

| 等级 | 含义 | 处置 |
|---|---|---|
| `[事实]` | 有外部证据：课程要求、公开答复、功能对比、实测数据 | 可直接作为需求 |
| `[约束推导]` | 由设计红线或已定约束必然导出，如"必须带出处""不得给剂量建议" | 可作为需求，但须注明推导自哪条约束 |
| `[假设]` | 无外部证据，按经验判断 | 可作为需求，但 `docs/08` 须为它安排验证或标为未验证 |

一级来源是 `docs/01` 的问题与目标；二级来源是约束 C-01～C-11 与设计红线；三级来源是 `docs/02` 的范围收缩与 `track/` 调研材料。

### 2.2 获取方法

采用四种方法，各自的局限一并说明：

1. **目标分解**：把 `docs/01` §6.3 的成功标准 S-01～S-07 与优化机会 O-01～O-12 逐条落到功能需求。局限：只覆盖已识别的机会，发现不了新需求。
2. **约束推导**：把 C-01～C-11 与设计红线转成硬性业务规则（BR-xx）。局限：约束只保证"不越界"，不保证"有用"。
3. **现状对照**：用 `docs/02` §3 的替代方式能力对比（L-08、L-09）确定必须具备与可以不做。局限：对照对象是通用工具，不是同类竞品。
4. **情景分析**：以 §3.3 的 SC-01～SC-09 为脚本，逐条走查"触发条件 → 用户动作 → 系统响应 → 期望结果"，据此确认需求是否覆盖了场景的全部步骤，并把场景中暴露的空缺补成需求。

情景分析在本项目中的作用有三点，也是选它的理由：

- **便于非技术方校验**：场景用学习者的日常说法描述（"写作业时核对某方组成"），用户不需要读懂需求条目就能判断对不对，因此能真正参与需求确认，而不是只在验收时被动签字。
- **能发现目标分解看不到的需求**：O-04 只说明"检索要覆盖方剂"，走查 SC-06"读医案时回查条文"才会追问到医案的检索入口（FR-308）、医案详情必须给出所用方与相关条文（FR-309），以及"医案不得充当证治推演依据"这条限制（BR-04、FR-309 的验收条件）。这类限制在目标层是看不出来的，只在具体场景里才会被追问出来。
- **保证用户处于主动位置**：需求的唯一可靠来源是用户。SC-01～SC-09 由使用场景出发而非由实现出发，讨论对象是"你要做什么"，用户因而能提出修改，而不是只能在给定方案上选是或否。

局限必须写明：本项目的场景由 `docs/01` §3.5 的六项任务推导而来，**没有做真实用户的情景走查**（`docs/01` §5.2 已承认未访谈）。因此情景分析在这里的作用是"内部一致性与覆盖度检查"，不是需求有效性的外部证据；SC 类需求在 §2.1 的证据等级一律按 `[假设]` 处理，`docs/08` 须安排验证。

### 2.3 需求编号规则

| 前缀 | 含义 | 示例 |
|---|---|---|
| FR-xyy | 功能需求，x 为模块号，yy 为序号 | FR-201 阅读原文 |
| NFR-xx | 非功能需求（性能、可靠性、出错处理、接口、约束等，类别见 §7.1） | NFR-03 检索响应时间 |

| FUT-xx | 将来可能提出的需求，尚未进入本期范围 | FUT-01 默写比对 |
| BR-xx | 业务规则 | BR-05 无出处不得输出 |
| UC-xx | 用例 | UC-05 阅读并定位篇条 |
| SC-xx | 使用场景（情景分析的脚本单元） | SC-05 考前一天自测 |
| DI-xx | 数据词典中的数据项 | DI-05 显示值 |

| AC-xxx-y | 某条需求的第 y 条验收条件 | AC-201-1 |

模块号：1 内容与导入／2 阅读／3 检索／4 练习／5 解释与拒答／6 治理／7 账号与学习记录／8 管理端／9 内容安全与合规。

编号跳号的处理：FR-107～FR-110 未分配，预留给书目申请的状态通知与撤回，本版不使用，编号不复用。其余跳号均属模块分段（如 FR-110 后接 FR-111 是申请与导入两段），不是遗漏。

NFR 采用连续编号而不按类别分段，与 `plan/02` §5 建议的 `NFR-类别-序号` 格式不同。理由：v0.1 的 NFR-01～NFR-14 已被 §7、§11.4、§12.3 引用，改成类别式编号会造成断链；类别归属改由 §7 的小节和 §7.1 的对应表表达，编号本身不含类别信息。若后续文档统一改用类别式编号，须一次性替换全部引用，不允许两套编号并存。

编号一经分配不再复用；废弃需求保留编号并标"作废"，不删除。

## 3. 用户角色与使用场景

### 3.1 角色定义

首版只有两个角色。`docs/02` §6.1 已确定系统不设教师角色，内容审核职责不由系统承担（C-01）。

| 角色 | 定义 | 端形态 |
|---|---|---|
| 学习者 | 正在修中医经典课程或以经典能力考试为目标的在校学生 | 微信小程序为主，PC 仅提示使用小程序 |
| 管理员 | 承担书目审核、导入、校对、治理队列处理的人 | PC Web |

管理员不是"超级用户"：除书目、导入、治理之外，管理员对学习功能的权限与学习者相同，不额外获取他人学习记录内容。

### 3.2 角色与任务的对应

| 任务（`docs/01` §3.5） | 学习者 | 管理员 |
|---|---|---|
| T-01 读某篇原文并理解上下文 | 主责 | 不涉及 |
| T-02 由方名核对组成与相关条文 | 主责 | 不涉及 |
| T-03 由药味反查方剂 | 主责 | 不涉及 |
| T-04 核对某结论的原文出处 | 主责 | 不涉及 |
| T-05 自测条文记忆与方证对应 | 主责 | 不涉及 |
| T-06 由医案回溯所用方与条文 | 主责 | 不涉及 |
| — 书目申请、导入、校对、治理 | 仅可提交申请 | 主责 |

### 3.3 关键使用场景

场景取自 `docs/01` §3.5 的六项任务，补充管理员侧三项。每条场景写明触发条件与期望结果，作为用例的输入，同时作为 §2.2 情景分析的走查脚本。

场景按"用户怎么描述这件事"写，不按"系统有哪些功能"写。判断一条场景写得好不好，标准是学习者能否只看这一行就说出"对，我要的就是这个"或"不对，我不是这么用的"——这是情景分析能让用户真正参与的前提。

| 编号 | 场景 | 触发 | 期望结果 |
|---|---|---|---|
| SC-01 | 课前预读某篇 | 只知道篇名或一句条文片段 | 定位到该篇，看到上下文与出处 |
| SC-02 | 写作业时核对某方组成 | 已知方名 | 得到组成、出处条文、其他典籍的记载差异 |
| SC-03 | 见到一味药想找相关方 | 已知单味药 | 得到包含该药的方剂清单 |
| SC-04 | 引用前确认原文 | 已知一句结论 | 得到可点击回溯的原文位置 |
| SC-05 | 考前一天自测 | 选定范围（章／节／方） | 得到判分结果、依据与错题入口 |
| SC-06 | 读医案时回查条文 | 已知医案 | 得到所用方、相关条文与出处 |
| SC-07 | 管理员收到书目申请 | 用户提交申请 | 依据准则判定通过或驳回，并留存理由 |
| SC-08 | 管理员导入新底本 | 书目已通过 | 完成结构化入库与逐段性质标注，产出校对任务 |
| SC-09 | 管理员处理缺口与冲突 | 队列有新条目 | 关闭、转化或标记为不可处理，全程留痕 |

关于 FR-116 逐段性质标注的必要性（Q-105 已答，负责人为项目负责人本人）：

1. **它决定"哪段能当证据"**。BR-01 要求任何输出带书名篇名，BR-04 要求只有"典籍原文"可作判据与出处。性质标错，等于把教学论述或医案当原文引用，同时违反设计红线一与红线五——这类错误在界面上看不出来，只有对着底本才知道。
2. **它不能被规则替代**。`docs/02` §7.9.4 实测：规则预标覆盖率 31%，且能认出的多是结构标题、分节标签与医案，"典籍原文"只命中 1.6%，而恰恰只有后者能作判据。因此人工不是抽查，而是逐段确认；抽样复核（FR-121）是在逐段确认之后的质量检查，两者不能互相顶替。
3. **成本随篇幅线性增长**。底本 40.9 万字、清洗后 7418 段，逐段确认是导入链里最大的一块人力（`docs/02` §9.2）。这也是 §10.2 把导入链放在关键路径上的原因。
4. **责任归属**。标注与校对由项目负责人（用户本人）承担，Q-105 已关闭；抽样比例定为不低于 10% 且每书不少于 100 段，按章节分层抽取，避免只抽到同一类段落。

- 用它作"初始序列"而非"自适应算法"：自适应需要足够的作答数据，首版量级下拟合不出可靠参数，反而会让间隔忽长忽短。答案对错只做"进一档／退一档"，规则确定、可复现、可解释。

- 参数可调：序列值存为配置而非硬编码，若后续有实测数据可替换，不影响 FR-407、FR-410、FR-412 的行为。

### 5.9 内容安全与合规（FR-9xx）

依据：平台要求提供"自定义发布内容"功能的小程序接入官方内容安全检测接口（文本 `msgSecCheck`、图片 `imgSecCheck`、音视频 `mediaCheckAsync`），且要求检测覆盖小程序内全部可发布的场景；未接入或覆盖不全，是提审被驳回的常见原因（REF-07、Q-102）。

本项目按"内容是否会被他人看到"划定检测范围，不做无差别检测：

| 编号 | 需求 | 验收条件 | 来源 | 首版 |
|---|---|---|---|---|
| FR-901 | 面向他人可见的用户提交文本（书目申请的书名、作者、目录、用途说明，以及缺口上报内容）须在入库前经平台内容安全接口检测；不通过则拒绝提交并提示"内容含违规信息"，不入库、不进队列 | 提交违规测试文本被拒且队列无新增；正常文本可正常入队 | REF-07 | 必做 |
| FR-902 | 检测接口不可用或超时时，提交暂存为待检，对管理员不可见，不阻断其他功能；恢复后自动补检，仍不通过则丢弃并提示用户 | 断网提交进入待检态；恢复后自动补检并给出结果 | NFR-21、NFR-25 | 必做 |
| FR-903 | 每次拦截留处置记录（时间、场景、结果），不保存违规正文 | 审计表可查记录，正文字段为空 | FR-806、NFR-08 | 必做 |

为什么只检测这两处、不检测笔记：

- 书目申请会进入管理员审核队列，缺口上报会进入治理队列，两者都会被他人看到，属平台定义的"自定义发布内容"，必须检测。
- 笔记与收藏仅本人可见，不构成发布，故不检测；但一旦启用导出或分享（FUT-06），分享路径必须一并接入检测，否则合规结论不成立。
- 检索与提问文本不展示给他人，不需检测；它们仍受 §7.8 的 INV-02 与 BR-12 约束。

FR-902 的边界：暂存待检不算"先发后审"，因为待检内容对任何人不可见。若平台后续要求"检测不可用时必须拒绝提交"，只需改 FR-902，不影响其他需求。

| 编号 | 需求 | 验收条件 | 来源 | 首版 |

| NFR-23 | "查不到"与"系统故障"在响应、日志与界面提示上可区分 | 拒答走 BR-02 的拒答流程并记缺口；故障给出重试指引；两者日志字段不同 | C-02、`docs/02` §7.5.1 | 必做 |

软件接口之外，教材的接口需求还包含人机接口、硬件接口与通信接口，此处一并说明，避免评审认为漏项：

- **人机接口**：学习者端只有微信小程序，管理端只有 PC Web（NFR-29）；不提供独立 App、桌面端与对外开放 API。界面结构与交互属 `docs/05`，本节只约束端形态。
- **硬件接口**：不使用任何专用硬件，不读取摄像头、麦克风、定位与通讯录（INV-05）。
- **通信接口**：首版不接第三方知识库实时查询（INV-08）；模型服务为可选能力且只在服务端调用（NFR-26）；微信侧只依赖登录授权与内容安全检测两个官方接口（NFR-25、FR-901）。

NFR-31 的依据与现状：

- **已核实的要求**（REF-07）：类目与功能必须相符；提供自定义发布内容的小程序必须接入官方内容安全接口并覆盖全部发布场景；小程序须完成备案。未接入或类目不符是提审被拒的高频原因。
- **在线教育类目的资质门槛**：该类目面向非个人主体，通常需要《营业执照》（经营范围含教育咨询）与 ICP 备案，部分情形还需增值电信业务经营许可证；具体清单以提审时类目详情页为准，属平台会调整的部分，不能凭本文档定稿。
- **本项目的主体现状**：3 人学生团队，当前不具备企业主体。因此本期交付以**本地演示环境**运行，不提审上线；若要走微信内上线，须先由学校或企业提供主体资质（Q-111）。这一条影响的是端形态能否落地，不是界面细节。
- **不做的规避动作**：不把教育内容伪装成"工具/资讯"类目申报，不引导用户到站外私下交易（REF-07）。这两条属平台明确的违规情形，成本高于收益。

**保留期总表（DR-13 的明细）**

| 数据类 | 起算点 | 期限 | 到期动作 |
|---|---|---|---|
| 底本显示值、章节树、性质标注、规则表、校勘记录 | 写入 | 永久 | 不删除 |
| 导入任务与报告 | 任务结束 | 永久 | 不删除 |
| 学习行为记录（进度、收藏、笔记、作答、复习） | 用户最后一次活跃 | 6 个月 | 删除 |
| 审计记录 | 写入 | 6 个月 | 脱去可关联到个人的标识，保留动作类型与时间 |
| 检测记录 | 写入 | 6 个月 | 同上（本就无正文） |
| 缺口记录 | 关闭 | 6 个月 | 清空问题原文，保留类型与涉及书目 |
| 数据缺陷 | 关闭 | 6 个月 | 删除记录 |
| 冲突记录 | 检出 | 随被比较实体保留 | 不单独删除 |
| 碰撞清单 | 导入批次 | 随批次保留 | 不删除 |
| 令牌吊销清单 | 令牌过期 | 即删 | 删除 |

三条口径。**①为什么保留期必须是需求而不是设计默认值**：删除与脱敏是可被外部检查的合规承诺（NFR-09），若期限由实现层自定，验收时只能检查"设计里写了 6 个月"，查不出"是否该是 6 个月"。写成需求后，期限本身成为可判定项。**②为什么是 6 个月**：见下方 Q-109 的口径说明，核心是同一条理由贯穿四类——既覆盖一个完整学期的使用周期，又不把责任无限期留在自己身上。**③为什么缺口与审计的处理不同**：审计的价值在"留下动作发生过"，不在"知道是谁做的"，故脱标识保留；缺口原文是用户提交内容，保留它没有治理价值，只有隐私风险，故清空正文、保留类型与书目。期限的变更不是运营配置，须改 DR-13 并由 `docs/08` 重新验证。

保留期限的作用与口径（Q-109 已答：半年）：

- **为什么要有期限，而不是永久保留**。两件事：一是复习排期依赖作答历史，到期清理会让长期不用的账号重新开始，这是可接受的功能代价；二是合规上的"最小必要"，无限期保存学习记录等于把数据泄露的责任长期留在自己身上，删除比加密更彻底。
- **为什么取半年**。艾宾浩斯式间隔的最长一档按 30 天计（§7 的 FR-409 与 §4 的 UC-11），半年约等于 6 个最长间隔，覆盖一个完整学期；短于 3 个月会让寒暑假回来的人丢失全部错题，长于 1 年则失去"最小必要"的意义。
- **为什么从"最后活跃"起算**。只要还在使用就不清理，避免"复习到一半记录被删"。若改成"自创建起固定 6 个月"，长期用户在学期末会被清空，体验上不可接受。
- **对用户可见的动作**：距到期不足 30 天时，在小程序内提示"学习记录将于某日清理"；不做静默删除。

| DI-15 | 复习状态 | 某学习对象的当前间隔与下次到期时间 | 数值 + 时间 | 对则拉长、错则缩短，无永久移出 |
| DI-16 | 缺口记录 | 拒答或用户上报形成的内容缺失条目 | 问题原文、时间、涉及书目、状态 | 状态流转留痕，不可补须填理由 |
| DI-17 | 冲突记录 | 同一实体跨底本的字段差异 | 实体、字段、两个以上取值及来源 | 并列保存，不裁决 |
| DI-18 | 审计记录 | 管理端关键操作的留痕 | 操作人、时间、对象、动作 | 不可修改、不可删除 |
| DI-19 | 篇内序号 | 内容单元在其所属篇章内的先后次序 | 整数 | 必填，篇内唯一且从 1 连续；由导入切分生成，不由条号推导；不参与归一，也不参与判据抽取（与 DI-04 分工：条号承载底本原样编号、可空，序号承载顺序与定位、不可空） |
| DI-20 | 原典归属 | 该段引自其他典籍时，原典的书名、篇名与条号 | 文本（三部分均可空） | 可空；非空时出处块须显示"转引自《X》"，不得与底本书名混淆；只对"典籍原文"段有意义。用于区分"底本里的这段"与"这段原本出自哪本书"（BR-01、FR-307） |

归一化的作用与范围（Q-104 已答：范围由项目负责人确定并承担）：

- **作用**：让同一段文字的不同写法（繁简、异体、全半角、标点与空白差异）在检索时能命中，同时不改动展示文本。它是"检索用副本"，不是"更好的原文"。
- **影响的功能**：FR-307（检索命中）、FR-302／FR-303（跨书组成差异比对）、FR-305（药味反查）、FR-306（类方比较）、FR-406（判据匹配）、NFR-06（可重建）、DR-02／DR-10。
- **不受影响的**：FR-206 与 BR-03——展示必须用显示值，归一值不得出现在正文里；FR-201 段落顺序。
- **本项目采用的范围**：不能只写"繁简、异体、全半角、标点、空白"五个词，那样每一词都有两种做法，等于没定。逐条定死如下：

| 项 | 采用的做法 | 不采用的做法及原因 |
|---|---|---|
| 全半角 | 只做 ASCII 与全角片假名等的全半角映射 | 不做全量 NFKC：它会把 `①`→`1`、`㈱`→`(株)`、`²`→`2`，改变符号语义，`①` 常被底本用作条号 |
| 繁简 | 统一转为**简体**作检索键，展示不变；一条原文只出一个检索键 | 不做简繁双键：会使一条记录对应两个归一值，与 DR-02 的"一列"冲突 |
| 异体字 | 只按指定的一表明细转换，表外不转；表名与版本随规则表登记 | 不写"常用异体"，"常用"没有判定标准，不可验收 |
| 标点 | **删除**（`。，、；：！？`、全角括号等） | 不做替换为半角：`桂枝汤。` 与 `桂枝汤` 仍不相等，等于没归一 |
| 空白 | **删除所有空白**（含全角空格、制表符） | 不做"折叠为单个空格"：中文无词间空格，折叠后 `桂枝 汤` 仍不等于 `桂枝汤` |
| 零宽与控制字符 | 删除 | — |
| 拉丁字母 | 转小写 | — |

- **标点为什么删而不换**：中文没有词间空格，`桂枝 汤` 必须能与 `桂枝汤` 相等；标点若只换成半角，`桂枝汤。` 仍不等于 `桂枝汤`。删除是唯一能让"标点差异"消失的做法。代价是跨句粘连（`……。麻黄……` 会连成一条串），因此检索按词或短语入口进行、不做整段比对，粘连不会直接影响结果。
- **明确不做**：通假字自动替换。理由：通假是多对多且依赖语境，自动合并会把不同条文归成一个检索键，污染判据与出处，而这两项正是本系统的红线；宁可查不到（走拒答），不可查错。
- **负责人**：归一化规则表与校勘记录均由项目负责人（用户本人）维护，Q-104 已关闭。

归一化只解决"字符层"，另外两层靠别的手段——这一层划分决定漏检从哪里来：

| 层 | 要解决的问题 | 靠什么 | 本项目是否做 |
|---|---|---|---|
| 字符层 | 同一个词的写法不同：繁简、异体、全半角、空白与标点 | 归一化规则（确定性字符映射） | 做 |
| 名称层 | 同一个实体的名称不同：正名、别名、简称（"小柴胡"与"小柴胡汤"） | 词表与别名表（Q-107） | 做，覆盖目标见 A-08 |
| 语义层 | 说法不同而所指相近（"解肌"与"解表"） | 语义检索或专家判断 | 不做；命中不到即走拒答 |

因此"归一规则不严谨会不会漏检"的答案是：会，但它只影响字符层；名称层的漏检靠词表解决，语义层是有意不做。三层混在一起谈，会把"规则不够全"和"本来就不打算做语义匹配"当成同一个问题。

归一化的边界：什么归、什么不归（Q-104 已答）：

| 归（只改写法，所指不变） | 不归（改动会改变所指，或需语境判断） |
|---|---|
| Unicode 兼容形式与全半角（`ＡＢＣ`→`ABC`、`（一）`→`(一)`） | 通假字（"蚤"作"早"） |
| 繁简（`黃連`→`黄连`） | 错别字、形近字（"桂技"→"桂枝"） |
| 常用异体字（`白朮`→`白术`） | 同义词、近义词（"解肌"与"解表"） |
| 标点符号、连续空白、零宽字符 | 简称与别名（"小柴胡"与"小柴胡汤"）——属名称层，交给词表 |
| 拉丁字母大小写 | 拼音、谐音 |
| — | 语序调整、增删字 |
| — | 中文数字与阿拉伯数字互转（"三"与"3"） |
| — | 剂量单位与数值换算（属红线，见 BR-06） |

三条判定原则，三条同时满足才归一，缺一不归：

1. 只改写法、不改所指；
2. 有对照表、可解释、可复现，不由模型生成；
3. 不依赖语境判断。

按此原则，通假字与错别字被排除：两者都必须读懂上下文才能确定原字，而"读懂"就是推断，猜错即篡改原文。数字与剂量换算被排除，是因为它们改变的是含义而不只是写法。

为什么不做相似度匹配（编辑距离、三元组、向量检索）：它们返回的是"最像的候选"，不是"是同一个词"。在必须给出处的场景里，把最像的候选当原文，就是编造出处。因此本项目只做精确匹配（归一后相等）加词表的确定性映射；匹配不上就返回未找到并走拒答（BR-02、FR-503）。若将来要做"你是不是想找 X"，只能作为提示，不得直接呈现该条原文。

归一化真正的风险不是漏检，而是**误合并**：

漏检的后果是"查不到"，走拒答即可；误合并的后果是"给出错误的出处"——把 A 条的内容当成 B 条的命中结果输出，等于编造引用，直接违反 BR-01 与设计红线五。v0.5 版之前本节只防了漏检，没有防这一类，是实质缺陷（v0.5 已补）。

已知的三种误合来源：

| 来源 | 例子 | 后果 |
|---|---|---|
| 一对多繁简字按字级盲转 | `乾薑`→`干姜`（对）与 `乾隆`→`干隆`（错） | 含"乾隆"的段落被当作"干"的命中返回 |
| 全量 NFKC 吞掉符号 | `①`→`1` | 条号 `①` 与正文数字混为一体，判据抽取错位 |
| 异体表范围过宽 | 古籍中本有区别的两个字被判为异体 | 两个不同所指被并成一个检索键 |

三道防线，缺一不可：

1. **词组级白名单**：一对多字（乾、著、发、后、里等）不参与字级转换，只在词组表命中的上下文里转换（`乾薑`→`干姜`，`乾隆`保持原样）。字级映射只用于无歧义字（`黃`→`黄`）。这也解释了为什么"白名单"必须定到词组粒度：字级白名单解决不了同一字在不同词里的不同读法。
2. **导入期碰撞检查**（DR-12）：两条显示值不同、归一值却相同，且差异无法由规则表逐字解释时，判为"隐式合并"，进人工确认队列，未确认不得入库。
3. **反向验收集**（`docs/08`）：至少 20 组"形似但非等价"的对照——乾薑／乾隆、白朮／白木、已／己／巳、桂枝汤／桂枝。要求全部不被合并、不产生误命中。只测"繁体异体能否命中"是只测了一半，误合并必须单独测。**用例已形成并跑通**：26 组负例（不得合并）、20 组正例（必须合并）、5 组顺序敏感、46 项幂等，见 `docs/05` §11.1 与 `track/exp/norm/test_normalize.py`；正式编号待 `docs/08` 登记。

规则不得过拟合到单本底本上。当前只实测了 REF-06 一本书，规则很容易从这本书的写法反推出来，结果是本书上表现好、换书即失效。三条约束：

1. 规则的依据只能是外部标准或明确的对照表，**不得从本书文本归纳**。例如不得因为本书里 `乾` 只出现在 `乾薑` 中，就断定 `乾→干` 恒成立。
2. 验收样例必须包含本书以外的文本（药典药名、其他典籍片段），否则测不出泛化能力，只能测出"样例背得熟"。
3. 覆盖率 95% 与规则范围只对首版底本成立；换书须按 A-07 重测切分、按本节重测归一，不得沿用旧结论。

可参考的实现思路（属 `docs/05` 的技术选型，本文只借其分层，不照搬其规则）：

- **Unicode 标准化 NFC／NFKC**（Unicode 标准附录 #15）：全半角与兼容字符处理的权威依据；重点是索引侧与查询侧必须使用同一种形式。注意 NFKC 的范围远大于"全半角"，会同时改写上标、圈码与合字，因此本项目只取其全半角子集，不整体套用（见上文"全半角"一行）。
- **OpenCC**（开源繁简转换）：支持字符级与**词组级**转换、异体字与地区用词配置（`s2t`／`t2s`／`s2tw` 等）；词组级转换正是缓解单字一对多误转的通行做法。
- **Elasticsearch ICU Analysis**（`icu_normalizer`、`icu_folding`）加中文分词插件：搜索引擎的标准结构是"索引与查询共用同一个 analyzer"，并把字符归一、分词、同义词拆成不同过滤器——与本节的"字符层／名称层"分层同构。
- **PostgreSQL** 的 `unaccent`、`tsvector`：中文全文检索需额外分词组件。**已实测**（`docs/05` §3.5）：zhparser 在 PG16 上可装、可用，但对"桂枝汤"漏 6.7%、"小柴胡汤"漏 12.8%，根因是词典把"汤加"收为词，使"桂枝汤加"被切开。故首版不建分词链，检索改用归一值等值匹配（实体）与归一值子串匹配（段落），口径见 `docs/05` §11.3。
- **异体字与古籍对照**：台湾教育部《异体字字典》是公开的异体字来源；CBETA、ctext 等古籍项目有繁简与校勘实践，但其具体规则本文未核实，仅作方向参考。

需要说清的边界：没有检索到专门针对中医古籍的公开归一化规范。上述参考都是通用文本处理与检索工程的做法，本项目借"分层＋两侧共用同一规则"的思路，不照搬任何一家的映射表；最终映射范围仍以本节的清单为准。

实现归属与四条硬约束（本文只约束这些，不规定做法）：

- **归一值是导入时算一次、存在内容单元上的属性**（DI-06、DR-02），不是每次检索时重算原文；查询时对用户输入跑同一套规则，再与库中的归一值列比对。两侧必须共用同一份规则实现，否则会对不齐。
- **规则表必须保存，且是一等数据**：它存映射、白名单、正则与版本号，须可回滚、可审计、有变更人；归一值只是它的产物，存在内容单元上。二者分开存不等于不保存规则——没有规则表就无法重算与对账，也无法回答"为什么这条检索结果变了"。
- **不存在"上一次的归一值"**：用户输入是临时的，按同一规则处理一次即用即弃，查询日志可留作统计但不是数据资产；有版本的是内容单元上的归一值（DR-10）。
- 本文要求四条：确定性（同输入必同输出）、幂等（对归一值再归一不变）、可重算（NFR-06）、不上屏（BR-03）。**规则顺序与表结构已定稿**：九步固定序列、版本号 `zh-norm-1.0`、三张规则表与一张外部表，见 `docs/05` §11.1；物理表结构见 `docs/06`。
- **规则顺序本身也是规则的一部分**：顺序一经确定须随规则表版本化，两侧调用同一实现；否则"先删标点再折叠空白"与"先折叠再删"会得到不同结果，重算对不上账。
- **判据字段从显示值抽取，归一值不参与判据抽取**。条号 `①`、`（十二）` 在归一后形态会变，若用归一值抽判据，FR-406 的匹配对象就被悄悄换掉了。
- 一对多的繁简字（如"乾""著"）不得盲目转换，须按**词组级**白名单处理；白名单增删与规则表同步升版本，否则重算结果无法对账。

数据存储：D1 内容库（书、篇、条、方、药、医案）、D2 学习记录库、D3 治理队列（缺口与冲突）、D4 审计与配置（词表、规则、文案）。

必须成立三条闭环，缺任一条即需求不闭环：

1. **出处闭环**：P2～P5 的输出都带 D1 的出处块，不允许任何加工产出无来源内容（BR-01、FR-504）。
2. **缺口闭环**：P5 拒答写入 D3，P6 处理 D3，处理结果回流到 P1 的补录（FR-601、FR-603）。
3. **判据闭环**：P4 只读 D1 中判据字段完整的记录，缺失项不进题目（FR-406、DR-08）。

### 9.2 实体与关系

| 实体 | 主要属性 | 关系 |
|---|---|---|
| 书目 | 书名、作者、朝代、版本、状态 | 1 书目 → N 篇章；1 书目 → N 内容单元 |
| 篇章 | 篇名、层级、序号 | 1 篇章 → N 内容单元 |
| 内容单元 | 标识、显示值、归一值、性质、条号 | N 内容单元 ↔ N 方剂（提及）；N 内容单元 ↔ N 医案 |
| 方剂 | 名称、别名、所属书目 | 1 方剂 → N 组成项；N 方剂 ↔ N 医案（所用方） |
| 药味 | 标准名、异名 | 1 药味 → N 组成项 |
| 组成项 | 原文用量文本 | 必挂 1 方剂 + 1 药味 |
| 医案 | 文本、所用方 | N 医案 ↔ N 内容单元（相关条文） |
| 用户 | 账号、端绑定 | 1 用户 → N 进度／收藏／笔记／作答 |
| 缺口 | 问题原文、状态、涉及书目 | 由拒答或用户上报产生 |
| 冲突 | 实体、字段、取值集合 | 每条须挂 2 个以上来源 |
| 支持对象（非核心实体） | 书目申请、导入任务、提交内容、题目、收藏、检测记录 | 由 §9.3 的状态表与 §5 的功能需求直接引用，属性见 `docs/04` §3.1；不参与上表三条基数约束，也不改变上表 10 个实体 |

三条基数约束是硬要求：内容单元必须同时挂书目与篇章（否则出处块不全，违反 BR-01）；组成项必须同时挂方剂与药味（否则反查与差异比对失效）；冲突记录必须挂两个以上来源（单来源不构成冲突）。

### 10.2 对进度的影响

关键路径是 **P1 导入与校对 → P2／P3 阅读与检索 → P4 练习 → P5 解释与拒答 → P6 治理**：出处闭环要求四类输出都依赖 D1 的完整数据，导入链不完备则后面全部无法验收（§9.1 的三条闭环）。`docs/02` §9.2 也把"内容导入与校对"列为相对工作量最高的一项，两者结论一致。据此修正三点：

1. **导入链前置且不可压缩**：FR-116（逐段性质标注）与 FR-122（质检门禁）是出处与判据的前提。为尽早出界面而跳过这两条，等于让后续所有输出都违反 BR-01，返工成本高于先做导入。
2. **练习的可用时间由导入质量决定，不由开发进度决定**：FR-406 只在判据完整时出题，`docs/02` §7.9.4 的抽样已显示条文识别率仅 1.6%，说明判据覆盖率是真实风险（A-09）。练习联调须排在至少一本书完成校对之后，否则联调对象是空数据集。
3. **出错处理与接口需求需要独立工作项**：NFR-19～27 共 9 条，原计划未列。它们分散在全部模块中，若不留时间，会在联调末期集中暴露，属于典型的进度风险。
4. **验收口径收紧会额外占用时间**：Q-106 要求 77 条（76 必做 + 1 条件）全部可验收，不再是"主流程可演示"。这意味着每条都要准备可复现的操作与证据，工作量高于演示式验收，而 `docs/02` §10.2 明确本次没有缓冲。结论是范围不能再扩：任何新增只能从 §11.4 的延后项里换，不能叠加。

关于"全部功能"的口径：本计划按 77 条（必做 + 条件）理解。条件项 FR-310 排在 P3 检索三条支路（UC-06／07／09）稳定之后，不单独占一段工期。若把 5 条延后项也计入，则须同时放开 2026-12-10 的交付期并追加人力，这两项不是需求文档能决定的，须先由 `docs/07` 重排后再回改本节。

A-08 里"词表"与"覆盖率"到底指什么（Q-107 已答：方案③，覆盖率 ≥95%）：

- **词表是三张名单**：方剂正名、方剂别名、药味名（含异名）。系统靠它把底本文字识别成"这是某个方／某味药"；检索、组成比对、出题都建立在识别结果上。它不改变展示（FR-206），只决定"能不能找到"。
- **来源有三种选法**：①**底本自身抽取**——只把这本书里出现的方名、药味收进来，人工确认。优点是判据一定来自底本，符合 BR-04；缺点是不认识同义词。②**外部权威资料导入**——用方剂学／中药学教材、药典或专业数据库的词条。优点是别名全、覆盖广；缺点是与底本用字可能不一致，需要人工对校。③**两者结合**——以底本抽取为准，外部资料只用于补别名与校验。
- **覆盖率怎么算**：能匹配上的实体数 ÷ 底本中实际出现的实体数。分母必须人工标注一遍才准；若不做全量，退而用"抽样 100 条中未匹配的比例"估计，并注明是估计值。
- **为什么必须定**：漏一个方名，FR-301 查不到；漏一味药，FR-305 反查缺一条；判据字段不全，FR-406 直接不出题。
- **已定（Q-107 已答）**：选 ③——底本抽取为准，外部资料（方剂学／中药学教材、药典、专业数据库）只用于补别名与校验。覆盖率目标 ≥95%；分母优先用人工标注的实体总数，不做全量时用抽样 100 条估计并注明是估计值。验收落在 FR-118 的导入报告上：匹配率低于 95% 即标注"不通过"并列出未匹配实体，补词表后可重跑。
