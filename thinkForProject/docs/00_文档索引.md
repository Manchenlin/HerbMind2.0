## 2. 为什么问题定义必须独立

可行性研究要判断一个已经明确的问题是否值得投入、是否具备实施条件。如果问题定义还混在立项背景里：

- 无法确认调研是否覆盖了真正的用户困难
- 无法区分“用户问题”和“技术方案”
- 可行性分析没有稳定的评价对象
- 后续需求容易直接跳到功能清单
- 答辩时说不清“为什么做这个系统”

因此本课程项目采用两条独立基线：

1. **问题基线：** 由 `01` 定义要解决的问题、服务对象、现状局限和成功标准。
2. **建设基线：** 由 `02` 判断哪些优化机会值得建设、采用什么方案、存在哪些风险。

## 3. 问题定义应回答的问题

`01_问题定义与项目背景.md` 至少回答：

1. 谁在什么学习场景中遇到什么困难？
2. 现有平台或替代方式为什么没有解决好？
3. 哪些问题是用户问题，哪些只是技术实现问题？
4. 本次系统建设准备优先解决哪几个问题？
5. 哪些问题明确不在本次范围内？
6. 怎样判断问题被解决了？

“当前现有平台有哪些局限性”应优先基于以下证据：

- 用户或教师反馈
- 学习任务观察
- 访谈、问卷或可用性测试
- 现有平台功能与实际使用流程的差距
- 同类学习平台的对比

不能仅凭代码质量、框架版本或数据库设计来判断课程项目要解决的问题。

## 5. 推荐写作顺序

```text
01 问题定义与项目背景
    ↓
02 可行性研究报告
    ↓
03 需求规格说明
    ↓
04 需求分析模型
    ↓
05 系统设计 ──→ 06 数据库设计
    ↓
08 质量与测试
    ↓
07 项目管理（可在 03 后并行）
    ↓
09 用户手册
    ↓
10 答辩与演示
```

说明：

- `07_项目管理计划` 依赖问题和需求规模，但不必等所有设计完成。
- `08_质量保证与测试计划` 必须在需求和设计稳定后完成，否则用例没有可靠依据。
- `10_答辩与演示` 必须引用其他文档的最终结论，不能单独维护另一套说法。

## 7. 计划建立的追踪关系

最终至少形成以下追踪链：

```text
问题定义
  → 干系人关注点
  → 项目目标与成功标准
  → 可行性结论
  → 功能/非功能需求
  → 用例
  → 设计模块
  → 测试用例
  → 验收结论
```

追踪矩阵建议放在 `08_质量保证与测试计划.md`，同时由 `03` 和 `05` 引用。矩阵字段至少包括：

| 字段 | 说明 |
|---|---|
| 需求编号 | `FR-*` 或 `NFR-*` |
| 需求摘要 | 一句话说明 |
| 优先级 | 必须、应该、可选 |
| 对应用例 | `UC-*` |
| 设计模块 | 模块编号或名称 |
| 测试用例 | `TC-*` |
| 验收状态 | 未验证、通过、失败、阻塞 |
