# 软件工程课程项目总体计划

> 本计划描述“怎样从零完成 HerbMind 的课程级系统分析与设计”，不是系统功能开发计划。
>
> 执行依据：`thinkForProject/README.md` 和 `thinkForProject/plan/00_全局记忆.md`。

**目标：** 形成一套从问题定义、可行性、需求、分析、设计到质量与答辩材料的完整软件工程课程成果。

**方法：** 先定义问题，再论证是否值得建设，随后建立需求基线；采用阶段化推进、阶段评审和双向追踪，不以现有代码反推设计。

**最终产物：** `thinkForProject/docs/` 下的正式课程文档，以及可复用的图示、追踪矩阵和答辩材料。

**当前状态：** P0～P4 已完成，P5 系统设计进行中（`docs/04` v0.7 待 G4；`docs/05` v0.19，§1～§11 与第二部分 §17、§19～§22 完成，仅 §12～§16 与 §18 待写；`docs/06` v0.4 草稿）；`docs/07`～`10` 未开始。

## 1. 项目范围

### 1.1 分析对象

HerbMind 中医经典学习平台。课程分析把它视为一个计划建设的系统，而不是对现有代码的说明文档。

### 1.2 核心业务边界

- 经典原文与章节阅读
- 方剂、药味、条文、医案检索
- 方剂—药味—原文之间的关系探索
- 病案练习、评分反馈、错题复习
- 带原文出处的学习问答
- 收藏、笔记、学习记录等个人学习支持
- 内容导入、审核与治理

### 1.3 不纳入范围

- 临床诊断、处方、剂量和真实患者管理
- 医院信息系统对接
- 无出处的功效推断和证治推演
- 为“技术展示”而添加、但无学习价值的模块

## 2. 质量原则

| 原则 | 具体做法 |
|---|---|
| 问题先行 | 每份文档先说明要解决的问题，再写功能或设计 |
| 证据支撑 | 现状局限来自用户反馈、任务观察或可核验资料，不来自代码缺陷猜測 |
| 单一事实源 | 需求正文只在 SRS 中定义，其他文档引用编号，不复制出多个版本 |
| 可追踪 | 问题 → 目标 → 需求 → 用例 → 设计 → 测试 → 验收保持对应关系 |
| 可验证 | 功能有验收条件，非功能需求有度量方式和目标值 |
| 不过度设计 | 每个设计决策说明理由、替代方案和代价 |
| 如实表达 | 事实、假设、决定、待确认项分开标注 |
| 课程概念服务内容 | 使用 UML、WBS、追踪矩阵等方法解决问题，不堆术语 |

### P1：课程要求校准与问题定义

**课程知识：** 软件工程概述、软件生命周期、问题定义、干系人、系统边界、目标与成功标准。

**主要任务：**

1. 确认 Q-001 至 Q-004。
2. 用具体学习场景陈述“谁在什么情况下遇到什么困难”。
3. 分析现有平台、替代方式和工作流程的局限性。
4. 区分用户问题、业务问题和技术实现问题。
5. 形成优化机会清单，只界定机会，不提前定技术方案。
6. 识别干系人及其关注点。
7. 定义项目愿景、范围和明确不做的事项。
8. 建立成功标准、初始术语表和项目约束。
9. 完成 `docs/01_问题定义与项目背景.md`。

**产物：**

- 问题陈述
- 现有平台局限与证据来源
- 优化机会清单和优先级
- 干系人清单
- 项目愿景与范围
- 成功标准
- 术语表初稿

**评审关口 G1：**

- 能用一段话说清“为谁解决什么问题”
- 每个关键问题都有来源或证据，而不是主观印象
- 优化机会没有提前写成具体技术方案
- 系统边界没有明显歧义

### P2：可行性研究

**课程知识：** 可行性分析、技术/经济/操作/进度/法律可行性、方案比较、风险。

**主要任务：**

1. 以 `docs/01` 的问题和优化机会为评价对象。
2. 提出至少两个可比较的建设方案。
3. 从技术、经济、操作、进度和法律角度分析可行性。
4. 估算成本、收益和关键资源。
5. 识别关键风险与前置条件。
6. 给出继续、缩小范围或终止的建议。
7. 完成 `docs/02_可行性研究报告.md`。

**产物：**

- 候选方案与范围
- 可行性分析表
- 成本、收益与资源估算
- 风险清单
- 推荐方案与结论

**评审关口 G2：**

- 每个“可行”结论都有依据
- 成本、进度或技术假设没有伪装成事实
- 推荐方案说明了取舍
- 没有越过问题基线擅自扩大范围

### P3：需求获取与需求规格

**课程知识：** 需求工程、需求分类、用例、功能需求、非功能需求、需求规格说明、需求验证。

**主要任务：**

1. 明确需求来源和获取方式，含情景分析及其局限。
2. 建立角色与用例清单。
3. 编写功能需求，分配 `FR-xxx` 编号。
4. 按教材的八类综合要求编写其余七类（性能、可靠性与可用性、出错处理、接口、约束、逆向需求、将来可能提出的需求），分配编号并给出度量或判定方式。
5. 定义业务规则、数据规则和设计红线。
6. 编写验收条件。
7. 建立需求优先级和版本范围。
8. 分析数据要求（五类数据描述、数据词典、采集方式、质量要求）。
9. 导出逻辑模型概览（数据流、实体关系、状态转换），写明与 04、06 的分工。
10. 修正开发计划（规模、进度、范围与资源的修正）。
11. 完成 `docs/03_需求规格说明书.md`。

**产物：**

- 角色与场景
- 用例清单
- 功能需求清单
- 八类综合要求清单
- 业务规则
- 数据要求与数据词典
- 逻辑模型概览
- 修正后的开发计划
- 需求追踪矩阵初稿

**评审关口 G3：**

- 每条需求可验证、无歧义
- 需求之间没有明显冲突
- 范围外内容没有被偷偷加入
- 关键需求都有验收条件

### P4：需求分析与建模

**课程知识：** 结构化分析、面向对象分析、UML、领域建模、行为建模。

**主要任务：**

1. 绘制用例图，写关键用例规约。
2. 建立领域概念模型和类图。
3. 用活动图描述学习、检索、练习和内容治理流程。
4. 用时序图描述关键交互。
5. 用状态图描述练习会话、内容审核等有状态对象。
6. 检查模型与 SRS 的一致性。
7. 完成 `docs/04_需求分析模型.md`。

**产物：**

- 用例图与用例规约
- 领域类图
- 活动图
- 时序图
- 状态图
- 模型—需求追踪表

**评审关口 G4：**

- 图中每个关键元素都能追溯到需求或用例
- 命名与术语表一致
- 图不是装饰，能回答具体分析问题

### P5：系统设计

**课程知识：** 总体设计（设计原理、模块独立性、软件结构图、面向数据流的设计）、详细设计（过程设计工具、判定表、界面详细设计、程序复杂度）、软件体系结构、接口设计、数据设计、部署设计。

**文档结构（D-052）：** `docs/05` 一份文档内部按教材"总体设计／详细设计"分为两部分，不拆成两个文件；`docs/06` 数据库设计保持独立。理由：教材区分的是设计深度，不是文档数量；课程未规定模板（Q-001），拆文件只会带来编号顺延与引用返工。

**与教材第 5 章九步的对应：** 设想供选方案→选取合理方案→推荐最佳方案，三步已在 `docs/02` 完成（PA／PB 比较与条件式结论），`docs/05` 只承接第 4 步之后：功能分解、设计软件结构、设计数据库、制定测试计划、书写文档、审查复审。不得在 05 重做方案比较，只在开头用一小节引出 02 的结论。

**主要任务：**

1. 给出逻辑架构、分层和模块职责。
2. 逐模块判定模块独立性：标明耦合类型（数据／标记／控制／公共／内容）与内聚类型（功能／顺序／通信／过程／时间／逻辑／偶然），对独立性不达标的模块给出拆分或改接口方案。
3. 绘制软件结构图（层次图），标出调用关系与传递的数据、控制信号；与架构图分开，前者画模块调用，后者画部署与分层。同时给出深度、宽度、扇出、扇入的取值与评价，检查每个模块的作用域是否落在其控制域内。
4. 用面向数据流的方法划分模块：导入链按变换分析（解析→切分→性质标注→质检入库），检索按事务分析（方名／药味／关键词／医案四个入口分派）。
5. 补一张系统流程图（画物理元素：程序、文件／库、人工过程、文档），与数据流图区分——前者是物理实现视图，后者是逻辑数据流。
6. 用 IPO 图或 PDL 简要描述每个细化后处理的算法，作为详细设计的输入。
7. 定义模块接口和依赖方向；接口按"简单且与功能一致"评价，避免整表传递（特征耦合）。
8. 设计数据模型、数据约束和数据生命周期（表结构在 `docs/06`）。
9. 设计关键业务流程和异常流程。
10. 设计用户界面总体结构（页面地图、导航、信息呈现规则），逐页细化放到详细设计部分。
11. 设计安全、权限、隐私和审计方案。
12. 设计性能、可用性、可维护性和部署方案。
13. 记录关键设计决策及替代方案（含被否方案与否决理由）。
14. 详细设计部分：用过程设计工具（PDL、活动图）给出关键模块的过程设计，至少覆盖导入、检索、判分、拒答判定四类。
15. 用判定表或判定树表示多条件规则：拒答条件（库内是否有依据、出处是否完整、段落性质是否为典籍原文、问题是否涉剂量）与出题资格（判据字段是否完整），不得写成散文。
16. 给出界面详细设计（页面状态、要素、错误与降级提示），与 `docs/03` 的 NFR-19～NFR-23 逐条对齐。
17. 给出关键模块的复杂度估计（分支数或 McCabe 环形复杂度），对高复杂度模块说明可测试性措施；模块保持单入口单出口、功能可预测。
18. 完成 `docs/05_系统设计说明书.md`（第一部分总体设计、第二部分详细设计）。
19. 完成 `docs/06_数据库设计说明书.md`。

**产物：**

- 架构图与模块清单
- 模块独立性判定表（耦合类型／内聚类型）
- 软件结构图（层次图）与深度／宽度／扇出／扇入评价
- 系统流程图（物理元素视角）
- IPO 图（细化处理算法）
- 变换分析与事务分析说明
- 接口清单
- 数据模型与表设计
- 关键时序和状态设计
- 界面总体结构与逐页详细规范
- 过程设计（PDL／活动图）与判定表
- 复杂度估计
- 部署拓扑
- 设计决策记录
- 总体设计评审与详细设计评审结论

**评审关口 G5：**

- 每个设计模块都有明确职责和需求来源
- 每个模块的耦合与内聚类型有明确判定，不是只写"高内聚低耦合"
- 软件结构图画的是调用关系，能与架构图区分开
- 关键判定规则（拒答、出题资格）以判定表或判定树表示，不写在散文里
- 接口、数据和异常处理闭合
- 没有用技术名词代替设计论证
- 安全与设计红线有对应措施
- 详细设计与既有实现的差异有清单（对应 RISK-19，`docs/02` §13.1）

### P8：整体一致性审查与导出

**主要任务：**

1. 检查术语、编号、角色和模块命名是否一致。
2. 检查问题、需求、分析、设计、测试追踪链是否闭合。
3. 检查图表与正文是否矛盾。
4. 检查课程模板、目录、页码和引用格式。

**评审关口 G8：**

- 所有正式文档通过一致性检查
- 无占位内容、无待定编号、无失效引用
- 提交文件可独立阅读

## 4. 文档依赖关系

```text
01 问题定义与项目背景
    ↓
02 可行性研究报告
    ↓
03 需求规格说明 ←──────────┐
    ↓                      │
04 需求分析模型             │
    ↓                      │
05 系统设计 ──→ 06 数据库设计 │
    ↓                      │
08 质量与测试 ──────────────┘
    ↓
09 用户手册
    ↓
10 答辩与演示
```

箭头表示主要依赖，不表示只能单向修改。任何上游变更都必须更新追踪矩阵并检查下游影响。

## 5. 每阶段工作循环

1. **确认输入：** 阅读全局记忆、上一阶段产物和未决问题。
2. **补充调研：** 仅收集课程方法或用户确认过的事实。
3. **形成中间产物：** 先写入 `track/`，保留推演和备选方案。
4. **编写正式文档：** 只把稳定结论写入 `docs/`。
5. **自检：** 按 `plan/02_文档规范.md` 检查完整性和一致性。
6. **评审：** 对照阶段关口逐项确认。
7. **更新状态：** 修改 `plan/00_全局记忆.md` 和决策日志。
8. **进入下一阶段：** 未通过关口不跨阶段堆文档。
