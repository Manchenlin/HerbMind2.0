# 软件工程课程项目总体计划

> 本计划描述“怎样从零完成 HerbMind 的课程级系统分析与设计”，不是系统功能开发计划。
>
> 执行依据：`thinkForProject/README.md` 和 `thinkForProject/plan/00_全局记忆.md`。

**目标：** 形成一套从问题定义、可行性、需求、分析、设计到质量与答辩材料的完整软件工程课程成果。

**方法：** 先定义问题，再论证是否值得建设，随后建立需求基线；采用阶段化推进、阶段评审和双向追踪，不以现有代码反推设计。

**最终产物：** `thinkForProject/docs/` 下的正式课程文档，以及可复用的图示、追踪矩阵和答辩材料。

**当前状态：** P0 前置工作完成，P1 尚未开始。

## 1. 项目范围

### 1.1 分析对象

HerbMind 中医经典学习平台。课程分析把它视为一个计划建设的系统，而不是对现有代码的说明文档。

### 1.2 核心业务边界

- 经典原文与章节阅读
- 方剂、药味、条文、医案检索
- 方剂—药味—原文之间的关系探索
- 病案练习、评分反馈、错题复习
- 带原文出处的学习问答
- 收藏、笔记、学习记录等个人学习支持
- 内容导入、审核与治理

### 1.3 不纳入范围

- 临床诊断、处方、剂量和真实患者管理
- 医院信息系统对接
- 无出处的功效推断和证治推演
- 为“技术展示”而添加、但无学习价值的模块

## 2. 质量原则

| 原则 | 具体做法 |
|---|---|
| 问题先行 | 每份文档先说明要解决的问题，再写功能或设计 |
| 证据支撑 | 现状局限来自用户反馈、任务观察或可核验资料，不来自代码缺陷猜測 |
| 单一事实源 | 需求正文只在 SRS 中定义，其他文档引用编号，不复制出多个版本 |
| 可追踪 | 问题 → 目标 → 需求 → 用例 → 设计 → 测试 → 验收保持对应关系 |
| 可验证 | 功能有验收条件，非功能需求有度量方式和目标值 |
| 不过度设计 | 每个设计决策说明理由、替代方案和代价 |
| 如实表达 | 事实、假设、决定、待确认项分开标注 |
| 课程概念服务内容 | 使用 UML、WBS、追踪矩阵等方法解决问题，不堆术语 |

## 3. 阶段路线

### P0：前置工作（已完成）

### P1：课程要求校准与问题定义

**课程知识：** 软件工程概述、软件生命周期、问题定义、干系人、系统边界、目标与成功标准。

**主要任务：**

1. 确认 Q-001 至 Q-004。
2. 用具体学习场景陈述“谁在什么情况下遇到什么困难”。
3. 分析现有平台、替代方式和工作流程的局限性。
4. 区分用户问题、业务问题和技术实现问题。
5. 形成优化机会清单，只界定机会，不提前定技术方案。
6. 识别干系人及其关注点。
7. 定义项目愿景、范围和明确不做的事项。
8. 建立成功标准、初始术语表和项目约束。
9. 完成 `docs/01_问题定义与项目背景.md`。

**产物：**

- 问题陈述
- 现有平台局限与证据来源
- 优化机会清单和优先级
- 干系人清单
- 项目愿景与范围
- 成功标准
- 术语表初稿

**评审关口 G1：**

- 能用一段话说清“为谁解决什么问题”
- 每个关键问题都有来源或证据，而不是主观印象
- 优化机会没有提前写成具体技术方案
- 系统边界没有明显歧义

### P2：可行性研究

**课程知识：** 可行性分析、技术/经济/操作/进度/法律可行性、方案比较、风险。

**主要任务：**

1. 以 `docs/01` 的问题和优化机会为评价对象。
2. 提出至少两个可比较的建设方案。
3. 从技术、经济、操作、进度和法律角度分析可行性。
4. 估算成本、收益和关键资源。
5. 识别关键风险与前置条件。
6. 给出继续、缩小范围或终止的建议。
7. 完成 `docs/02_可行性研究报告.md`。

**产物：**

- 候选方案与范围
- 可行性分析表
- 成本、收益与资源估算
- 风险清单
- 推荐方案与结论

**评审关口 G2：**

- 每个“可行”结论都有依据
- 成本、进度或技术假设没有伪装成事实
- 推荐方案说明了取舍
- 没有越过问题基线擅自扩大范围

### P3：需求获取与需求规格

**课程知识：** 需求工程、需求分类、用例、功能需求、非功能需求、需求规格说明、需求验证。

**主要任务：**

1. 明确需求来源和获取方式。
2. 建立角色与用例清单。
3. 编写功能需求，分配 `FR-xxx` 编号。
4. 编写非功能需求，分配 `NFR-xxx` 编号，并给出度量方式。
5. 定义业务规则、数据规则和设计红线。
6. 编写验收条件。
7. 建立需求优先级和版本范围。
8. 完成 `docs/03_需求规格说明书.md`。

**产物：**

- 角色与场景
- 用例清单
- 功能需求清单
- 非功能需求清单
- 业务规则
- 需求追踪矩阵初稿

**评审关口 G3：**

- 每条需求可验证、无歧义
- 需求之间没有明显冲突
- 范围外内容没有被偷偷加入
- 关键需求都有验收条件

### P4：需求分析与建模

**课程知识：** 结构化分析、面向对象分析、UML、领域建模、行为建模。

**主要任务：**

1. 绘制用例图，写关键用例规约。
2. 建立领域概念模型和类图。
3. 用活动图描述学习、检索、练习和内容治理流程。
4. 用时序图描述关键交互。
5. 用状态图描述练习会话、内容审核等有状态对象。
6. 检查模型与 SRS 的一致性。
7. 完成 `docs/04_需求分析模型.md`。

**产物：**

- 用例图与用例规约
- 领域类图
- 活动图
- 时序图
- 状态图
- 模型—需求追踪表

**评审关口 G4：**

- 图中每个关键元素都能追溯到需求或用例
- 命名与术语表一致
- 图不是装饰，能回答具体分析问题

### P5：系统设计

**课程知识：** 软件体系结构、模块化、高内聚低耦合、接口设计、数据设计、界面设计、设计模式、部署设计。

**主要任务：**

1. 给出逻辑架构、分层和模块职责。
2. 定义模块接口和依赖方向。
3. 设计数据模型、数据约束和数据生命周期。
4. 设计关键业务流程和异常流程。
5. 设计用户界面结构、导航和信息呈现规则。
6. 设计安全、权限、隐私和审计方案。
7. 设计性能、可用性、可维护性和部署方案。
8. 记录关键设计决策及替代方案。
9. 完成 `docs/05_系统设计说明书.md`。
10. 完成 `docs/06_数据库设计说明书.md`。

**产物：**

- 架构图与模块清单
- 接口清单
- 数据模型与表设计
- 关键时序和状态设计
- 界面结构与交互规范
- 部署拓扑
- 设计决策记录

**评审关口 G5：**

- 每个设计模块都有明确职责和需求来源
- 接口、数据和异常处理闭合
- 没有用技术名词代替设计论证
- 安全与设计红线有对应措施

### P6：项目管理、质量保证与测试

**课程知识：** WBS、进度计划、责任分配、风险管理、配置管理、软件质量、测试层次、测试方法、验收测试。

**主要任务：**

1. 建立 WBS 和里程碑。
2. 定义角色、职责和协作机制。
3. 制定进度、资源和沟通计划。
4. 建立风险登记册和应对方案。
5. 制定配置管理和变更控制规则。
6. 制定质量目标、评审流程和测试策略。
7. 编写关键测试用例和验收标准。
8. 建立问题—需求—设计—测试追踪矩阵。
9. 完成 `docs/07_项目管理计划.md` 和 `docs/08_质量保证与测试计划.md`。

**产物：**

- WBS
- 里程碑与进度表
- 责任矩阵
- 风险登记册
- 配置管理方案
- 测试策略与用例
- 追踪矩阵

**评审关口 G6：**

- 计划中的任务能覆盖全部交付物
- 风险有触发条件和应对措施
- 关键需求都有对应测试
- 质量目标可度量

### P7：用户文档与答辩准备

**课程知识：** 软件文档、用户手册、验收演示、项目总结。

**主要任务：**

1. 编写面向学习者的使用说明。
2. 编写管理员和内容维护说明。
3. 准备答辩提纲、演示路径和常见问题。
4. 将技术语言转换为听众能理解的表达。
5. 完成 `docs/09_用户手册.md` 和 `docs/10_答辩与演示.md`。

**评审关口 G7：**

- 演示路径能覆盖核心价值
- 用户文档不依赖开发者口头解释
- 答辩材料能说明取舍，而非只展示功能

### P8：整体一致性审查与导出

**主要任务：**

1. 检查术语、编号、角色和模块命名是否一致。
2. 检查问题、需求、分析、设计、测试追踪链是否闭合。
3. 检查图表与正文是否矛盾。
4. 检查课程模板、目录、页码和引用格式。
5. 按课程要求导出 Word 或 PDF。
6. 形成最终提交清单。

**评审关口 G8：**

- 所有正式文档通过一致性检查
- 无占位内容、无待定编号、无失效引用
- 提交文件可独立阅读

## 4. 文档依赖关系

```text
01 问题定义与项目背景
    ↓
02 可行性研究报告
    ↓
03 需求规格说明 ←──────────┐
    ↓                      │
04 需求分析模型             │
    ↓                      │
05 系统设计 ──→ 06 数据库设计 │
    ↓                      │
08 质量与测试 ──────────────┘
    ↓
09 用户手册
    ↓
10 答辩与演示
```

箭头表示主要依赖，不表示只能单向修改。任何上游变更都必须更新追踪矩阵并检查下游影响。

## 5. 每阶段工作循环

1. **确认输入：** 阅读全局记忆、上一阶段产物和未决问题。
2. **补充调研：** 仅收集课程方法或用户确认过的事实。
3. **形成中间产物：** 先写入 `track/`，保留推演和备选方案。
4. **编写正式文档：** 只把稳定结论写入 `docs/`。
5. **自检：** 按 `plan/02_文档规范.md` 检查完整性和一致性。
6. **评审：** 对照阶段关口逐项确认。
7. **更新状态：** 修改 `plan/00_全局记忆.md` 和决策日志。
8. **进入下一阶段：** 未通过关口不跨阶段堆文档。
