# 课程文档写作规范

> 本规范保证不同阶段、不同会话写出的文档使用同一套结构、术语和编号。

## 1. 基本规则

1. 正式文档使用中文，语气客观、准确、可验证。
2. 不出现“我认为”“AI 生成”“当前代码显示”等不属于正式文档的表述。
3. 不使用无法验收的形容词，例如“界面友好”“性能优秀”“功能强大”。
4. 事实、决定、假设和待确认项必须区分。
5. 正文中引用需求、用例或设计时使用稳定编号，不重复定义。
6. 图表必须有编号、标题和文字说明；图不能替代正文论证。
7. 每份正式文档末尾包含“待确认事项”和“变更记录”。

## 2. 内容标记

过程记录中使用以下标记，正式文档中只在确有必要时保留：

| 标记 | 含义 |
|---|---|
| `[事实]` | 已由用户、课程材料或可核验资料确认 |
| `[决定]` | 已作出的项目或设计决定 |
| `[假设]` | 当前采用但尚未确认的前提 |
| `[待确认]` | 缺失且会影响后续结构的信息 |
| `[课程概念]` | 用于解释所采用的软件工程方法 |
| `[设计红线]` | 不可违反的产品、安全或伦理约束 |

## 3. 文件命名

正式文档采用：

```text
docs/01_问题定义与项目背景.md
docs/02_可行性研究报告.md
docs/03_需求规格说明书.md
docs/04_需求分析模型.md
docs/05_系统设计说明书.md
docs/06_数据库设计说明书.md
docs/07_项目管理计划.md
docs/08_质量保证与测试计划.md
docs/09_用户手册.md
docs/10_答辩与演示.md
```

过程文件采用：

```text
track/YYYY-MM-DD_主题.md
```

已经形成固定索引的文件保留 `00_` 编号。文件改名必须同步更新所有引用。

## 4. 文档状态

| 状态 | 含义 |
|---|---|
| 待编写 | 只有计划，没有正文 |
| 草稿 | 内容不完整，允许结构性修改 |
| 待评审 | 作者自检完成，等待用户确认 |
| 已确认 | 用户认可，作为下游文档基线 |
| 待更新 | 上游变化导致内容需要修订 |
| 已归档 | 被新版本替代，仅保留历史 |

状态变化必须记录在 `docs/00_文档索引.md`。

## 5. 编号规则

| 类型 | 格式 | 示例 |
|---|---|---|
| 功能需求 | `FR-领域-序号` | `FR-CONTENT-001` |
| 非功能需求 | `NFR-类别-序号` | `NFR-PERF-001` |
| 业务规则 | `BR-序号` | `BR-003` |
| 用例 | `UC-序号` | `UC-012` |
| 设计决策 | `DD-序号` | `DD-005` |
| 接口 | `API-模块-序号` | `API-CONTENT-002` |
| 数据实体 | `ENT-名称` | `ENT-FORMULA` |
| 测试用例 | `TC-模块-序号` | `TC-SEARCH-004` |
| 风险 | `RISK-序号` | `RISK-007` |

编号一经使用不回收、不复用。删除需求时保留编号并标记“废止”。

## 6. 正式文档通用结构

每份文档原则上包含：

```text
1. 文档信息
   1.1 目的
   1.2 范围
   1.3 读者对象
   1.4 术语与缩略语
   1.5 参考资料
2. 正文主体
3. 约束与假设
4. 待确认事项
5. 变更记录
```

不同文档按需要扩展，但不得省略“目的、范围、假设、变更记录”。

## 7. 各文档最低内容要求

### 01 问题定义与项目背景

- 项目背景与领域情境
- 目标用户、干系人及其学习任务
- 待解决问题的正式陈述
- 现有平台、替代方式与工作流程的局限性
- 局限性的证据来源：反馈、观察、访谈或对比
- 问题优先级：本次要解决、暂不解决、明确不解决
- 优化机会初筛：只描述机会，不提前定方案
- 项目愿景、成功标准和可观察的改善指标
- 系统范围、外部依赖与非目标

### 02 可行性研究报告

- 问题基线与建设目标
- 候选建设方案及方案边界
- 技术、经济、操作、进度和法律可行性
- 成本、收益和关键资源
- 风险、前提和依赖
- 方案比较与推荐结论
- 需要缩小、延期或放弃的范围

### 03 需求规格说明书

- 需求来源与获取方法
- 用户角色与使用场景
- 用例清单
- 功能需求及验收条件
- 非功能需求及度量
- 业务规则和设计红线
- 假设、依赖和范围外事项
- 需求追踪矩阵初稿

### 04 需求分析模型

- 用例图与关键用例规约
- 领域概念模型和类图
- 活动图、时序图、状态图
- 模型与需求的对应关系
- 分析中发现的需求缺口

### 05 系统设计说明书

- 设计目标与约束
- 架构风格、分层和模块职责
- 模块接口和依赖关系
- 关键业务流程与异常流程
- 界面结构与交互原则
- 安全、权限、审计和隐私设计
- 性能、可用性、可维护性设计
- 部署拓扑
- 设计决策与替代方案

### 06 数据库设计说明书

- 数据设计目标
- 概念模型与逻辑模型
- 实体、属性、主键和外键
- 约束、索引和完整性规则
- 数据生命周期与备份恢复
- 数据安全与敏感信息处理
- 关键查询与性能考虑

### 07 项目管理计划

- 项目组织与角色
- WBS 和工作包
- 里程碑与进度计划
- 资源与沟通计划
- 风险登记册
- 配置管理与变更控制
- 质量与交付物检查

### 08 质量保证与测试计划

- 质量目标
- 评审与静态检查
- 测试层次和测试类型
- 测试环境与数据
- 关键测试用例
- 需求—设计—测试追踪
- 缺陷管理与验收标准

### 09 用户手册

- 系统用途与适用人群
- 首次使用和主要任务
- 阅读、检索、练习、问答的操作说明
- 常见问题与错误处理
- 使用边界和安全提示

### 10 答辩与演示

- 问题与目标
- 需求与关键取舍
- 架构与模块
- 演示路径
- 质量与测试证据
- 风险、限制与后续计划
- 预期问答

## 8. 图表规范

1. 图号连续：`图 3-1` 表示第 3 章第 1 幅图；表号同理。
2. 每幅图先说明“它要回答什么问题”，再给图。
3. UML 图必须使用统一术语并标注角色、边界和关系方向。
4. Mermaid 只用于适合文本维护的图；复杂 UML 图在导出前检查渲染结果。
5. 任何图都不能只存在于对话里，必须落到 `docs/` 或 `track/` 文件。
6. 图中英文缩写首次出现必须有中文解释。

## 9. 需求质量检查

一条合格需求应满足：

- 有唯一编号
- 有明确主体和行为
- 有触发条件或使用场景
- 有可观察结果
- 有验收条件
- 不把实现方案写成需求
- 与其他需求不矛盾

不合格示例：

```text
系统应使用 Redis 提升性能。
```

合格写法：

```text
NFR-PERF-001：在 50 个并发学习请求下，常用检索接口的 95% 响应时间应不超过 2 秒。
```

## 10. 追踪规则

最小追踪链：

```text
干系人关注点 → 需求 → 用例 → 设计模块 → 测试用例 → 验收结果
```

每条关键需求至少能回答：

1. 为什么需要它？
2. 哪个用例体现它？
3. 哪个设计模块实现它？
4. 哪个测试验证它？

无法回答时，不允许把需求标记为“已覆盖”。

## 11. 设计红线在文档中的表达

- 只描述查证、引用和学习辅助，不写诊断、处方或剂量建议。
- 涉及中医内容时，区分“原文”“注释”“学习提示”，不把推测写成事实。
- 涉及问答和生成能力时，必须写清出处、拒答和人工复核机制。
- 涉及用户数据时，说明最小收集、权限和删除机制。

## 12. 版本与变更

文档头部记录：

```text
版本：v0.1
状态：草稿
最后更新：YYYY-MM-DD
变更摘要：本次修改了什么，为什么修改
```

版本规则：

- `v0.x`：结构和内容仍在讨论
- `v1.0`：用户确认，可作为下游基线
- 上游变更导致下游受影响时，下游状态改为“待更新”

## 13. 提交前检查

- [ ] 标题、编号、目录和正文一致
- [ ] 没有占位符和未解释缩写
- [ ] 图表编号连续且正文有引用
- [ ] 需求、设计、测试编号可追踪
- [ ] 没有把假设写成事实
- [ ] 没有诊疗建议和无出处推断
- [ ] 已按课程模板检查格式
- [ ] 已记录变更和待确认事项
